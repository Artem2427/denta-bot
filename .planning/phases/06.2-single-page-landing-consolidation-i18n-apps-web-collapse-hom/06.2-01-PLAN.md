<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser → `apps/web/proxy.ts` | Every request (except matcher-excluded `/blog`, `/api`, `/_next`, `/_vercel`, files-with-dots) passes through next-intl's locale-detection middleware before Next.js route resolution — reads `Accept-Language` header and a next-intl-set locale cookie, both attacker-influenceable inputs. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06.2-01 | Tampering | `apps/web/proxy.ts` / `i18n/routing.ts` | low | mitigate | `hasLocale(routing.locales, requested)` guard in `i18n/request.ts` means an attacker-crafted `Accept-Language`/cookie value can only ever resolve to one of the 3 statically-defined locales (`uk`/`ru`/`en`) or fall back to `defaultLocale` — no arbitrary string ever reaches a dynamic import path or redirect target. |
| T-06.2-02 | Tampering (open redirect) | `shared/components/locale-switcher.tsx` | low | mitigate | Switcher links are 3 hardcoded literal paths (`/`, `/ru`, `/en`) with zero user-supplied redirect target — no `?next=` or similar param is read, eliminating open-redirect risk by construction. |
| T-06.2-03 | Information Disclosure | `/blog` chrome falling back to `uk` locale via cookie/header absence | low | accept | Deliberate, documented behavior (D-09): chrome translation is in-scope for `/blog` too, and falling back to whichever locale the visitor's cookie/header resolves to (including `uk` default) is the intended UX, not a data leak — no sensitive data involved, purely a UI-string language choice. |
</threat_model>
