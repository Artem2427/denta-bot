## Summary

This phase is two intertwined efforts: (1) collapsing four routed pages (`/`, `/prices`, `/demo`, `/contacts`) into one scrolling `/` page composed from ~11 anchor sections sourced from a Claude-Design canvas export (`DentaBot Landing.dc.html`), while `/blog` and `/blog/[slug]` stay untouched, real, and Ukrainian-only; and (2) installing the monorepo's first i18n system (`next-intl`) so `/`, `/ru`, `/en` all serve the landing page + site chrome (Header/Footer) in the appropriate language, while blog remains outside that system entirely.

The route consolidation is the easier half: `apps/web`'s Phase 01.1/06.1 `dt-*` primitive set (`Section`, `Container`, `Eyebrow`, `SectionHeading`, `PremiumCard`, `Reveal`, `StaggerGrid`) already covers everything the design file needs, and most existing Home/Prices/Contacts module components map closely onto the design's sections (Problem/Solution ↔ problem section, Features ↔ features grid, PricingCards ↔ pricing section, ContactForm ↔ lead section). The `Section` component already accepts a plain `id` prop, so `id="pricing"` / `id="lead"` anchor targets are zero-cost. The one real content risk found: **no global `scroll-behavior: smooth` exists yet** in `premium-theme.css` (only its reduced-motion `auto !important` override exists), and **no section currently reserves `scroll-margin-top` for the `fixed` header** (h-16/h-20) — both must be added or anchor navigation will visually clip under the sticky header.

The i18n half is the harder half because it's genuinely new infrastructure with an unresolved architectural fork: `next-intl`'s standard App Router setup (verified against current official docs, 2026-08-19) puts all locale-aware pages under an `app/[locale]/` segment, while Next.js's static-route-priority rule lets `app/blog/` coexist as a sibling outside `[locale]` for D-09's Ukrainian-only requirement — that part is solid and low-risk. What's *not* a documented recipe is what `Header`/`Footer` (global site chrome, rendered on every route including `/blog`) should do on `/blog`, which has no locale segment at all. Research surfaces two viable designs (see Open Questions) and recommends one, but this is a decision the planner (or a quick CONTEXT follow-up) should lock explicitly before task-writing, since it changes where `Header`/`Footer` live in the layout tree.

A second infrastructure risk: **Next.js 16 renamed `middleware.ts` to `proxy.ts`** (exported function renamed `middleware`→`proxy`), confirmed via official Next.js 16 docs and a next-intl-specific migration writeup. `apps/web` is on Next.js 16.2.0 and has no existing middleware file — the new i18n proxy must be created as `apps/web/proxy.ts`, not `apps/web/middleware.ts`, or requests will silently bypass locale detection.

Finally, `PricingPlan` reseeding (D-04) has no existing seed-script precedent to extend cleanly: `packages/db/prisma/seed.ts` currently only bootstraps the single `PlatformAdmin` row and its own header comment explicitly forbids `deleteMany`/truncate on any table. A `PricingPlan` reseed must be additive/upsert-style (matched by `name`, since there's no unique constraint on `name` and adding one would be a schema change outside D-04's "no schema change" boundary).

**Primary recommendation:** Use `next-intl` v4.13.7 with `localePrefix: 'as-needed'`, structure the codebase as `apps/web/i18n/{routing,request,navigation}.ts` + `apps/web/proxy.ts` + `apps/web/app/[locale]/{layout,page}.tsx`, keep `apps/web/app/blog/` and `apps/web/app/blog/[slug]/` exactly where they are today (outside `[locale]`, excluded from the proxy matcher), and resolve the Header/Footer-on-blog question by wrapping `apps/web/app/layout.tsx` (root) in `NextIntlClientProvider` unconditionally so Header/Footer always render via `useTranslations`/`getTranslations`, falling back to `uk` (the default locale) whenever no `[locale]` segment is present in the request (i.e., on `/blog`).

### Pattern 1: `next-intl` App Router routing setup (verified against official docs, 2026-08-19)

**What:** The `routing.ts` + `request.ts` + `navigation.ts` + `proxy.ts` + `[locale]/layout.tsx` five-file pattern is next-intl's documented, current (Next.js 16-compatible) setup for URL-based locale routing.
**When to use:** Any App Router app adding URL-prefixed i18n — exactly this phase's D-08.
**Example:**
```typescript
// Source: https://next-intl.dev/docs/routing/configuration (CITED, fetched 2026-08-19)
// apps/web/i18n/routing.ts
import { defineRouting } from 'next-intl/routing';

export const routing = defineRouting({
  locales: ['uk', 'ru', 'en'],
  defaultLocale: 'uk',
  localePrefix: 'as-needed', // '/' = uk (unprefixed), '/ru/...', '/en/...'
});
```

```typescript
// Source: https://next-intl.dev/docs/getting-started/app-router/with-i18n-routing (CITED, fetched 2026-08-19)
// apps/web/i18n/navigation.ts
import { createNavigation } from 'next-intl/navigation';
import { routing } from './routing';

export const { Link, redirect, usePathname, useRouter, getPathname } =
  createNavigation(routing);
```

```typescript
// Source: next-intl official docs, cross-checked against multiple community
// guides for the stable (non-experimental) API surface — RECOMMENDED variant,
// does not depend on Next.js 16's newer `next/root-params` import (see note below)
// apps/web/i18n/request.ts
import { hasLocale } from 'next-intl';
import { getRequestConfig } from 'next-intl/server';
import { routing } from './routing';

export default getRequestConfig(async ({ requestLocale }) => {
  const requested = await requestLocale;
  const locale = hasLocale(routing.locales, requested)
    ? requested
    : routing.defaultLocale;

  return {
    locale,
    messages: (await import(`../messages/${locale}.json`)).default,
  };
});
```

**Note on an alternative, newer API:** The current official docs (fetched 2026-08-19) show a Next.js-16-native variant of `request.ts` using `import * as rootParams from 'next/root-params'` instead of destructuring `requestLocale` from `getRequestConfig`'s callback argument. `[CITED: next-intl.dev, low confidence on stability]` — `next/root-params` is a newer Next.js API and its availability in Next.js 16.2.0 **stable** (vs. canary) was not independently verified this session; `apps/web`'s `next.config.js` also has no `experimental` block today. **Recommend the `requestLocale`-based variant above** (years-stable API, no experimental flag dependency) unless the planner independently confirms `next/root-params` works on `next@16.2.0` stable.

```typescript
// Source: https://www.buildwithmatija.com/blog/next-intl-nextjs-16-proxy-fix (CITED)
// and https://next-intl.dev/docs/routing/middleware (CITED)
// apps/web/proxy.ts — Next.js 16 renamed middleware.ts -> proxy.ts; the
// exported function is also renamed. apps/web has NO existing
// middleware.ts/proxy.ts today (verified: find turned up nothing), so this
// is a net-new file, not a migration.
import createMiddleware from 'next-intl/middleware';
import { routing } from './i18n/routing';

export const proxy = createMiddleware(routing);

export const config = {
  // Exclude /blog and /blog/[slug] (D-09) in addition to the standard
  // next-intl exclusions (api/_next/_vercel/files-with-dots).
  matcher: ['/((?!api|_next|_vercel|blog|.*\\..*).*)'],
};
```

```typescript
// Source: https://next-intl.dev/docs/getting-started/app-router/with-i18n-routing (CITED)
// apps/web/app/[locale]/layout.tsx
import { hasLocale } from 'next-intl';
import { NextIntlClientProvider } from 'next-intl';
import { setRequestLocale } from 'next-intl/server';
import { notFound } from 'next/navigation';
import { routing } from '@/i18n/routing';

export function generateStaticParams() {
  return routing.locales.map((locale) => ({ locale }));
}

export default async function LocaleLayout({
  children,
  params,
}: {
  children: React.ReactNode;
  params: Promise<{ locale: string }>;
}) {
  const { locale } = await params;
  if (!hasLocale(routing.locales, locale)) notFound();
  setRequestLocale(locale);

  return (
    <NextIntlClientProvider>{children}</NextIntlClientProvider>
  );
}
```

### Pattern 2: Coexisting localized + unlocalized routes (D-09)

**What:** `app/blog/` and `app/blog/[slug]/` stay exactly where they are today — siblings of `app/[locale]/`, never nested inside it.
**When to use:** Any route that must be permanently excluded from the locale system, per D-09.
**Why it works:** Next.js App Router route resolution gives **static segments priority over dynamic segments at the same tree level** `[CITED: nextjs.org routing docs + confirmed via community discussion, cross-checked]`. `app/blog` (static) wins the `/blog` URL outright; `app/[locale]` (dynamic) is never consulted for that path. This requires **zero restructuring of the existing blog route files** — they can be left completely untouched.
**Required companion change:** The `proxy.ts` matcher must explicitly exclude `/blog` (see Pattern 1's matcher regex above) — otherwise next-intl's middleware would still run its locale-detection/redirect logic against `/blog` requests before Next.js's route resolution ever gets a chance to apply static-priority, potentially issuing a spurious redirect (e.g., cookie-remembered `ru` → attempting `/ru/blog`, a URL that doesn't exist in the unlocalized blog structure).

### Pattern 3: Server Component data fetching composed with i18n (Q3)

**What:** The existing Phase 6 pattern — Server Component `fetch()` against `/public/*`, pass data as props to a client "module" component — composes cleanly with `next-intl`'s server-side `getTranslations()`. Both are `await`-based Server Component APIs; there's no conflict.
**When to use:** The `#pricing` section, which must render **translated UI chrome** (labels: "Прозорі тарифи…" / "Transparent pricing…") around **untranslated CMS data** (plan names "Старт"/"Клініка"/"Мережа", `description`, `features[]` — all Ukrainian-only in the DB per D-11, since `PricingPlan` has no locale field).
**Example:**
```typescript
// apps/web/app/[locale]/page.tsx (excerpt) — Server Component
import { getTranslations } from 'next-intl/server';
import { getServerApiUrl } from '@/shared/lib/api-url';
import type { PricingPlan } from '@/modules/landing/types';

export default async function LandingPage() {
  const t = await getTranslations('pricing');
  const res = await fetch(`${getServerApiUrl()}/public/pricing-plans`, {
    next: { revalidate: 60 },
  });
  const plans = (await res.json()) as PricingPlan[];

  return (
    <section id="pricing">
      <h2>{t('heading')}</h2>       {/* translated chrome */}
      {/* plans.map(...) renders plan.name/description/features verbatim — Ukrainian regardless of active locale, by design (D-11) */}
    </section>
  );
}
```
This is the **confirmed pattern for D-11's open question**: translate the surrounding UI chrome, leave the fetched `PricingPlan` content exactly as returned by the API — no client-side or server-side "translation at render time" of DB content is implemented. On `/ru` and `/en`, a visitor will see translated headings/labels/CTAs but Ukrainian plan names/descriptions/features. **This should be called out explicitly to the client/stakeholder as a known, deliberate limitation** — it directly affects sales copy quality on the two "growth" locales.

### Anti-Patterns to Avoid

- **Nesting `app/blog` inside `app/[locale]`:** Would force blog to require a locale prefix and would need dummy `/ru/blog`, `/en/blog` routes or fallback logic — directly contradicts D-09. Keep it a sibling.
- **Re-fetching translated messages per-component:** Load `messages/{locale}.json` once via `getRequestConfig`, not scattered `import()` calls in individual components — the wired `next-intl` provider pattern already handles this.
- **Translating `PricingPlan` DB content client-side with a translation API/library:** Out of scope and unrequested (D-11 says "left to research/planning" but the finding above is the standard/expected answer — don't build a runtime machine-translation layer for CMS content this phase).
- **Using `middleware.ts` instead of `proxy.ts`:** Will trigger a deprecation warning at best, or (per the CVE-2025-29927 context that motivated the Next.js 16 rename) may not run with the same guarantees. Use `proxy.ts` and the `proxy` export name.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| URL-based locale detection/redirect, cookie persistence, `Accept-Language` fallback | A custom `[locale]` param parser + manual redirect logic in a hand-rolled middleware | `next-intl`'s `createMiddleware(routing)` | Handles the "as-needed" prefix logic (unprefixed default + prefixed others), superfluous-prefix redirects, and cookie-based preference memory correctly — this is exactly the kind of stateful edge-case logic (what happens when a `ru`-cookied user hits unprefixed `/`?) that's easy to get subtly wrong by hand |
| Locale-aware internal linking (`<Link>` that automatically prefixes `/ru/...` when the current locale is `ru`) | Manually prepending `` `/${locale}` `` to every `href` in Header/Footer/CTA buttons | `next-intl`'s `createNavigation(routing)` → `Link`/`redirect`/`usePathname`/`useRouter` | One missed manual prefix = a broken cross-locale link; the generated helpers guarantee consistency and also correctly *omit* the prefix for the default locale under `as-needed` |
| Comparison-table feature-union derivation (retained from Phase 6, unrelated to this phase but still live in `comparison-table.tsx`) | — | Already handled (`Array.from(new Set(plans.flatMap(...)))`) | No change needed; flagged only so the planner doesn't accidentally rebuild it while migrating the section |

**Key insight:** Every piece of "custom i18n logic" this phase might be tempted to write by hand (prefix stripping, redirect-on-missing-locale, cookie memory) is precisely what `next-intl`'s router/middleware/navigation trio already solves; hand-rolling any of it reintroduces bugs the library has already had years to shake out (5.75 years old, 489 releases).

## Common Pitfalls

### Pitfall 1: Sticky header clips anchor-scroll targets
**What goes wrong:** Clicking `href="#pricing"` scrolls the browser so the target section's top edge lands directly under the `fixed top-0` Header (h-16 mobile / h-20 desktop), hiding the section heading.
**Why it happens:** Neither `apps/web/app/premium-theme.css` nor `apps/web/app/globals.css` currently declares `scroll-behavior: smooth` on `:root`/`html` — the only related rule found is the reduced-motion override `scroll-behavior: auto !important` inside a `@media (prefers-reduced-motion: reduce)` block `[VERIFIED: apps/web/app/premium-theme.css:80-91]`, which implies smooth scrolling was anticipated but the base declaration was never added. Nor does any section carry `scroll-margin-top`/`scroll-mt-*` to compensate for the fixed header's height.
**How to avoid:** Add `html { scroll-behavior: smooth; }` (base declaration, the existing reduced-motion override already turns it off correctly for accessibility) and give every anchor-target `<Section id="...">` a `scroll-mt-16 lg:scroll-mt-20` className matching Header's `h-16 lg:h-20` `[VERIFIED: apps/web/shared/components/header.tsx:44]` (`className="flex h-16 items-center justify-between lg:h-20"`).
**Warning signs:** Manual click-through QA on `#pricing`, `#lead`, and any other anchor target — visually check the section heading isn't hidden under the header on both mobile and desktop breakpoints.

### Pitfall 2: `AdminTab`/`BotTab` are NOT on the bespoke `dt-*` design system — embedding them breaks visual consistency and reintroduces emoji
**What goes wrong:** If the "Claude's Discretion" demo/how-it-works section keeps the existing interactive bot+admin simulation (`modules/demo/demo-tabs.tsx`), the embedded result will look visually inconsistent with the rest of the landing page.
**Why it happens:** Per `.claude/CLAUDE.md`'s explicit carve-out, the Demo page's admin-panel simulation is the ONE place in `apps/web` that intentionally stays on `@repo/ui` (shadcn) components, not the bespoke `dt-*` system — confirmed by reading `admin-tab.tsx`, which imports `Badge`/`Button`/`Card`/`Table` from `@repo/ui` `[VERIFIED: apps/web/modules/demo/admin-tab.tsx:1-16]`. It also still contains decorative emoji in its sidebar nav (`📊 Dashboard`, `📅 Записи`, `👨‍⚕️ Лікарі`, `🧑‍🤝‍🧑 Пацієнти`, `⚙️ Налаштування`) `[VERIFIED: apps/web/modules/demo/admin-tab.tsx:134,141,148,155,162]` — this directly conflicts with the client's established no-emoji constraint from Phase 06.1 (evidenced by the shipped commits "remove leading emoji from bot demo scenario messages" and "replace decorative emoji with Phosphor icons"). Separately, `bot-tab.tsx`'s own `seedGreetings()` function still hardcodes a tooth emoji: `'Вітаю! Я DentaBot 🦷'` `[VERIFIED: apps/web/modules/demo/bot-tab.tsx:27]` — the 06.1 emoji-removal pass only touched `_data.ts`'s scripted scenario messages `[VERIFIED: apps/web/modules/demo/_data.ts:1-27, confirmed no emoji present]`, not this separate hardcoded greeting.
**How to avoid:** If the interactive simulation is kept (planner/researcher's leaning per CONTEXT.md), budget explicit cleanup tasks: (1) strip the 5 emoji from `AdminTab`'s sidebar buttons, replacing with Phosphor icons to match the 06.1 pattern; (2) strip the 🦷 emoji from `BotTab`'s `seedGreetings()`; (3) accept (or explicitly flag to the client) that `AdminTab`'s `@repo/ui` styling will look visually distinct from the surrounding `dt-*` sections — this is by design per CLAUDE.md, not a bug, but it's a real visual seam worth calling out before it ships on the primary landing page rather than a secondary `/demo` route.
**Warning signs:** Any grep for `📊|📅|👨‍⚕️|🧑‍🤝‍🧑|⚙️|🦷` inside `apps/web/modules/demo/` should return zero results before this phase ships.

### Pitfall 3: `PricingPlan` reseed must not violate `seed.ts`'s own "never truncate" convention
**What goes wrong:** A naive reseed implementation does `prisma.pricingPlan.deleteMany()` then `createMany()`.
**Why it happens:** `seed.ts`'s own header comment is explicit: *"Never deleteMany/truncate any table — this script only ever writes the single admin row."* `[VERIFIED: packages/db/prisma/seed.ts:1-2]` — extending this file (or writing a sibling script following its convention) with a destructive reseed breaks an established safety convention, and in a shared dev/staging DB could also nuke rows created independently via `platform-admin`'s CRUD UI between now and execution.
**Why it's non-trivial:** `PricingPlan` has no `@unique` field besides `id` (a `cuid()`) `[VERIFIED: packages/db/prisma/schema.prisma:118-133]` — there's no natural key to `prisma.pricingPlan.upsert({ where: {...} })` against without a schema change (prohibited by D-04's "no schema change").
**How to avoid:** Write an idempotent reseed as `findFirst({ where: { name } })` → `update` if found, `create` if not, for each of the 3 plans (Старт/Клініка/Мережа) — matched by `name`, which is stable across reruns even without a unique constraint. Recommend adding this as a new exported function in `seed.ts` (or a sibling script, e.g. `packages/db/prisma/seed-pricing.ts`) rather than mixing it into the existing admin-bootstrap `main()`, to keep the "never truncate" convention legible per-file. `[ASSUMED — mechanism is Claude's discretion per D-05; this is the recommended lowest-friction option consistent with the existing file's conventions, not a verified existing pattern]`

### Pitfall 4: Design file's per-plan `cta`/`tag`/`for` fields don't exist on the real `PricingPlan` API response
**What goes wrong:** Copying the design file's `planData` array (which has `for`, `tag`, `cta`, `items[]` per plan) literally into the landing page's pricing section will not compile/render against the actual API shape.
**Why it happens:** The real `PricingPlan` DTO (confirmed via schema + `modules/prices/types.ts`) has `{ id, name, monthlyPrice, yearlyPrice, description, features, isPopular }` — no `for`, `tag`, `cta`, or `items` fields `[VERIFIED: packages/db/prisma/schema.prisma:118-133 and apps/web/modules/prices/types.ts:1-9]`. The design file is a static mock, not the real data contract.
**How to avoid:** Map design intent onto real fields: `for` → fold into `description` (already free-text), `tag` "Найпопулярніший" → driven by the existing `isPopular` boolean + `PremiumBadge` (already implemented in `pricing-cards.tsx`), `items[]` → `features[]` (already implemented), `cta` (per-plan distinct button label like "Почати"/"Замовити демо"/"Обговорити") → either hardcode a fixed mapping by plan `name` in the component, or keep the existing single "Обрати план" CTA — Claude's discretion, not blocking, but should be a conscious choice during planning rather than an accidental copy-paste of the design's mock CTA strings as if they were real data.

### Pitfall 5: Two near-duplicate FAQ components exist today
**What goes wrong:** Planning might accidentally keep both `modules/contacts/faq-accordion.tsx` (8 questions) and `modules/prices/faq-accordion.tsx` (7 questions) as separate files feeding into one consolidated FAQ section, causing confusion about which is canonical.
**Why it happens:** Both were built independently in earlier phases for their respective standalone pages; both are near-identical in structure (`[VERIFIED: apps/web/modules/contacts/faq-accordion.tsx:1-63, apps/web/modules/prices/faq-accordion.tsx:1-58]`), differing only in content.
**How to avoid:** Consolidate into a single `modules/landing/faq.tsx` sourcing questions from the design file's 5-question FAQ list (per CONTEXT.md's "Specific Ideas" section) rather than merging both existing 7/8-question lists; delete both old files once no page imports them.

## Open Questions

1. **How should `Header`/`Footer` render on `/blog`, which has no `[locale]` URL segment?**
   - What we know: `next-intl`'s documented pattern nests all locale-aware content under `app/[locale]/`; `/blog` must stay a sibling per D-09. `Header`/`Footer` are currently rendered from the root `app/layout.tsx`, which wraps both `/blog` and (after this phase) `/[locale]/*`.
   - What's unclear: Whether wrapping the ROOT layout in `NextIntlClientProvider` (so `getRequestConfig`'s `requestLocale` resolves to `undefined` → falls back to `routing.defaultLocale` ('uk') on `/blog`, giving Header/Footer working `uk` translations there for free) is a supported/working pattern, or whether it requires the request to pass through a `[locale]` segment to get message context at all. This determines whether Header/Footer need ONE implementation (recommended) or TWO (a translated `[locale]`-aware version + a separate hardcoded-`uk` version for `/blog`).
   - Recommendation: Spike this specific combination (root layout `NextIntlClientProvider` + a sibling unlocalized route) early in Wave 1, before building out all landing sections on top of it — it's a foundational risk, not a cosmetic one. If it doesn't work cleanly, fall back to Header/Footer accepting an optional `locale` prop with a hardcoded `uk` default for use outside `[locale]`.

2. **Does the locale switcher appear on `/blog`, and where does it navigate to?**
   - What we know: D-09 confirms blog has no translated content. D-08 requires a locale switcher somewhere in site chrome.
   - What's unclear: On `/blog`, does the switcher (a) not render at all, (b) render but navigate to `/ru`/`/en` (the landing page in that locale, since blog has no equivalent), or (c) render disabled/grayed?
   - Recommendation: Option (b) — always navigate to the landing page root in the target locale — is the simplest, most defensible UX and requires no conditional rendering logic. Confirm with a CONTEXT follow-up or lock as a planning default.

3. **Exact demo/how-it-works section composition (interactive simulation vs. static explainer) — CONTEXT.md's own "Claude's Discretion" item.**
   - What we know: The interactive `BotTab`/`AdminTab` simulation exists, works, and is more compelling than a static screenshot per CONTEXT.md's own leaning.
   - What's unclear: Whether embedding a `@repo/ui`-styled interactive widget (see Pitfall 2) inside a `dt-*`-styled landing page reads as an intentional "different surface, demo mode" moment (acceptable) or a jarring inconsistency (not acceptable) at the scale of a single continuous scroll (as opposed to its current isolated `/demo` route).
   - Recommendation: Keep the interactive simulation (per CONTEXT.md's lean) but budget the Pitfall 2 cleanup tasks (emoji removal) explicitly, and treat the `@repo/ui`-vs-`dt-*` visual seam as a known, accepted tradeoff rather than a silent gap — flag for a UI review checkpoint during execution/verification, similar to how 06.1 handled "no more than two coral elements" as a judgment-call review gate rather than a mechanical rule.
