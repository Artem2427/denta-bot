## Fixed Issues

### CR-01: Pricing-plans fetch failure crashes the entire landing page, not just the pricing section

**Files modified:** `apps/web/app/[locale]/page.tsx`
**Commit:** `c4b1704`
**Applied fix:** Wrapped the `GET /public/pricing-plans` fetch in try/catch and dropped the `!res.ok` throw. `plans` now starts as `[]` and is only populated when the response is `ok`; any network error or non-OK response falls through silently, leaving the rest of the landing page (Hero, ChannelMarquee, ProblemSolution, HowItWorks, AdminShowcase, Features, Reviews, LeadSection, Faq, and the shared Header/Footer) to render normally with an empty pricing section instead of throwing and taking down the whole page.

### WR-01: Retired-route redirects always land on the default (uk) locale, discarding the visitor's ru/en context

**Files modified:** `apps/web/app/contacts/page.tsx`, `apps/web/app/prices/page.tsx`, `apps/web/app/demo/page.tsx`
**Commit:** `03e87f1`
**Applied fix:** Each retired route stub now reads the `NEXT_LOCALE` cookie (set by next-intl's middleware on every request that passes through `proxy.ts`, e.g. `/en`, `/ru`) via `next/headers`' `cookies()`, validates it against `routing.locales` with `hasLocale`, and falls back to `routing.defaultLocale` when absent/invalid. The redirect itself now goes through `redirect({ href, locale })` from `@/i18n/navigation` (next-intl's locale-aware redirect helper) instead of a raw `next/navigation` redirect to an unprefixed path. This means a visitor on `/en` who clicks the demo tab's "Connect your clinic" CTA (which links to `routes.contacts` = `/contacts`) now lands back on `/en/#lead` instead of being silently dropped to the Ukrainian landing page. First-ever direct visits to these routes with no prior locale cookie still fall back to `uk` (same as before — no regression).

### WR-02: Hero section has hardcoded Ukrainian strings that never localize

**Files modified:** `apps/web/modules/landing/hero.tsx`, `apps/web/modules/landing/hero-notification-badge.tsx`, `apps/web/messages/uk.json`, `apps/web/messages/ru.json`, `apps/web/messages/en.json`
**Commit:** `1033b69`
**Applied fix:** Added `hero.reminderBadge` and `hero.notificationBadge` keys to all three message files (translated per-locale, matching the tone of the surrounding hero copy). `hero.tsx` now renders `t('reminderBadge')` for its own bell-icon badge and passes `t('notificationBadge')` down as a `text` prop to `HeroNotificationBadge`, which was changed from a hardcoded string to a `{ text: string }` prop-driven client component.

### WR-03: Pricing section badge and price suffix are hardcoded Ukrainian, contradicting the component's own i18n contract

**Files modified:** `apps/web/modules/landing/pricing-section.tsx`, `apps/web/messages/uk.json`, `apps/web/messages/ru.json`, `apps/web/messages/en.json`
**Commit:** `ee5fb33`
**Applied fix:** Added `pricing.popularBadge` and `pricing.perMonth` keys to all three message files and swapped the two hardcoded strings (`Популярний` badge, `/міс` suffix) for `t('popularBadge')` / `t('perMonth')`. Also updated the component's own top-of-file comment, which previously claimed only "heading, billing toggle, CTA, footnote" were translated, to reflect that all chrome (including the popular badge and per-month suffix) is now translated — plan `name`/`description`/`features` remain intentionally Ukrainian-only per D-11 (API-sourced data, out of scope).

### WR-04: `proxy.ts` matcher regex lacks path-segment boundaries, silently misrouting any future path that merely starts with an excluded literal

**Files modified:** `apps/web/proxy.ts`
**Commit:** `55ffdcb`
**Applied fix:** Anchored every excluded literal in the matcher's negative lookahead to a path-segment boundary (`(?:/|$)`), applying the reviewer's suggested regex verbatim: `'/((?!api/|_next/|_vercel/|blog(?:/|$)|prices(?:/|$)|demo(?:/|$)|contacts(?:/|$)|.*\\..*).*)'`. Verified behaviorally with a standalone Node regex test against the review's exact example paths: `/blog`, `/prices`, `/demo`, `/contacts` remain excluded (middleware skipped, as intended); `/blogging`, `/pricesss`, `/democracy`, `/contactsupport` now correctly fall through to the locale middleware instead of silently bypassing it. `/en`, `/ru`, `/` (locale-aware routes) are unaffected.

### WR-05: `apps/web/i18n/navigation.ts` is entirely unused dead code

**Files modified:** none (resolved as a side effect of WR-01, commit `03e87f1`)
**Commit:** `03e87f1`
**Applied fix:** No separate change was needed — the WR-01 fix wires `redirect` from `@/i18n/navigation` into all three retired-route stubs (`apps/web/app/contacts/page.tsx`, `apps/web/app/prices/page.tsx`, `apps/web/app/demo/page.tsx`), which is exactly the "wire it in" option the finding suggested. Verified with a fresh grep (`grep -rn "from '@/i18n/navigation'"` across `apps/web`) that the module now has three real importers and is no longer dead code.

### WR-06: `seed-pricing.ts` upsert is non-atomic (check-then-act race) and matches on a non-unique field

**Files modified:** `packages/db/prisma/seed-pricing.ts`
**Commit:** `866ffe0`
**Applied fix:** Wrapped each plan's `findFirst` → `update`/`create` sequence in `prisma.$transaction(async (tx) => { ... }, { isolationLevel: 'Serializable' })`. This does not require the out-of-scope schema change (no `@unique` added to `name`, per D-04/D-05 and the finding's own note that a schema change is out of scope) and does not introduce `deleteMany`/truncate. Under concurrent invocations, one transaction now fails with a serialization error instead of both silently creating duplicate rows — an acceptable outcome for a manually-triggered, re-runnable seed script.
