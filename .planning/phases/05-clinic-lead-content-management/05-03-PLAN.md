## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| PlatformAdmin → POST /leads/:id/convert | The only write path in this phase that creates a NEW Clinic from user-submitted (Lead) data rather than direct admin input — the Lead's `name`/`clinicName`/`email` fields originate from `apps/web`'s public forms (Phase 6), so this endpoint is the first place that data crosses into a Clinic record |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-05-03-01 | Tampering | Lead-to-Clinic conversion (2-write operation) | high | mitigate | Both writes happen inside a single `prisma.$transaction` — never two independent calls; a crash mid-way leaves neither write committed |
| T-05-03-02 | Denial of Service | Repeated convert attempts on an already-converted Lead | low | mitigate | Idempotent-safe: re-checked inside the transaction (not just before it) so a race between the pre-check and the transaction can't create a duplicate Clinic |
| T-05-03-03 | Tampering | `UpdateLeadStatusDto` mass assignment (`updatedById`) | high | mitigate | Never declared on the DTO; set exclusively from `@CurrentUser().sub` |
| T-05-03-04 | Information Disclosure | LeadsController responses (raw Prisma Lead objects, including submitted PII: name/email/phone/message) | medium | accept | Only reachable by an authenticated PlatformAdmin (global AccessTokenGuard); this is exactly the "unified Lead inbox" data the requirement asks PlatformAdmin to view — no further redaction is meaningful for its own operators |

</threat_model>
