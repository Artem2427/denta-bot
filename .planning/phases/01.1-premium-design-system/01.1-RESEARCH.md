## Summary

This phase builds a self-contained, apps/web-scoped design-system layer that must coexist — without touching or depending on — `packages/ui`'s existing Tailwind v4 token set, since `packages/ui/styles/theme.css` is still imported into `apps/web/app/globals.css` and still backs the `@repo/ui` primitives used for the Demo page's admin-panel simulation. The core technical risk is not "which library" but "how do two independent Tailwind v4 `@theme` token sets and two independent primitive-component systems live in the same app without visual or naming collisions." The recommended approach is additive layering: keep the existing `@import '@repo/ui/styles/theme.css';` (needed for the admin-simulation), and add a second, distinctly-named token block (e.g. `--dt-navy`, `--dt-teal`, `--dt-coral`, `--dt-warm-white`, `--dt-graphite`, `--dt-sage`, `--dt-amber`) in a new apps/web-local CSS file so Tailwind v4 generates non-colliding utilities (`bg-dt-navy`, `text-dt-coral`, etc.) alongside `@repo/ui`'s existing `bg-background`/`text-primary`/etc.

For motion, `motion` (the current package name for what was `framer-motion`, v13.0.0) is the correct pick over GSAP: it has full, current React 19 support, its declarative variant/`AnimatePresence` API maps naturally onto the chat-bot's message-sequencing and scroll-reveal requirements (D-19–D-24, D-28), and — while GSAP became fully free in April 2025 (Webflow acquisition) removing its historical licensing friction — GSAP's imperative timeline API is a worse fit for React's render model and gets no RSC-specific advantage over Motion (both need `'use client'` wrapper components). Icons: `@phosphor-icons/react` (v2.1.10) is confirmed to coexist cleanly with the existing `lucide-react` dependency (independent tree-shaking, no shared namespace) — Phosphor drives all new premium-site iconography, lucide-react stays scoped to the `@repo/ui`-based admin-simulation only, per D-02.

Fonts: the CONTEXT.md's assumption that "Inter Display" is directly available via Google Fonts or Fontsource does not hold up — neither Google Fonts nor Fontsource lists a separate "Inter Display" family/package. It is real, but only as static woff2 files in the official `rsms/inter` GitHub release archive (v4.1, OFL-1.1 license), requiring manual download and self-hosting via `next/font/local`. Regular "Inter" remains available zero-config via `next/font/google` (Next.js downloads and self-hosts it at build time — no runtime CDN calls, satisfying D-45 without any manual asset management). Scroll-reveal (D-28, D-44) should be a small hand-rolled `useInView`-style hook wrapping the native `IntersectionObserver` API in a Client Component — no third-party scroll library needed, and this matches D-44's explicit instruction to avoid "heavy scroll-animation libraries beyond the chosen motion library."

**Primary recommendation:** Motion (`motion` npm package) for animation, `@phosphor-icons/react` for icons, a hand-rolled native-`IntersectionObserver` hook for scroll-reveal, `next/font/google` Inter for body text plus a manually self-hosted "Inter Display" (from the official `rsms/inter` v4.1 release) via `next/font/local` for headings — with a second, distinctly-namespaced Tailwind v4 `@theme` token block added to `apps/web` alongside (not replacing) the existing `@repo/ui/styles/theme.css` import.

### Pattern 1: Dual Tailwind v4 token layering (no `tailwind.config.js` — CSS-first config)
**What:** Two independent `@theme` blocks in scope simultaneously — `@repo/ui`'s existing one (imported via `@import '@repo/ui/styles/theme.css';`, unchanged) and a new one this phase adds, using a distinct naming prefix to prevent utility-class collisions.
**When to use:** Always, for this phase — this is the mechanism that makes D-01 ("not built on `packages/ui`") and D-02 (admin-simulation still needs `@repo/ui`) simultaneously true in one Next.js app.
**Example:**
```css
/* apps/web/app/premium-theme.css — NEW, imported from globals.css after @repo/ui's theme.css */
@theme {
  --color-dt-navy: #1A2B3D;
  --color-dt-teal: #2C7A7B;
  --color-dt-warm-white: #FAFAF8;
  --color-dt-coral: #E86B5A;
  --color-dt-graphite: #2D3436;
  --color-dt-sage: #7A9E7E;
  --color-dt-amber: #D4A24C;
  --radius-dt-card: 0.625rem;   /* 10px, within D-12's 8-12px range */
  --radius-dt-input: 0.375rem;  /* 6px, D-12 */
}
```
This makes `bg-dt-navy`, `text-dt-coral`, `rounded-dt-card`, etc. available as Tailwind utilities, with zero collision risk against `@repo/ui`'s `bg-background`/`text-primary`/`rounded-lg` tokens (different property names entirely). Source: Tailwind v4 CSS-first `@theme` directive behavior, confirmed against this repo's existing `packages/ui/styles/theme.css` (`@theme inline { --color-brand: var(--brand); }` pattern already in use for Phase 1's brand token) `[VERIFIED: codebase — packages/ui/styles/theme.css read directly]`.

### Pattern 2: Client-only scroll reveal wrapping server-rendered children (avoids hydration mismatch)
**What:** A small `'use client'` component that takes `children` as a prop (content stays server-renderable), attaches a `ref`, and toggles a CSS class or `data-state` attribute once `IntersectionObserver` fires.
**When to use:** Every scroll-triggered reveal (D-28) and any element needing hover/scroll-based motion.
**Example:**
```tsx
// apps/web/shared/components/use-in-view.ts
'use client';
import { useEffect, useRef, useState } from 'react';

export function useInView<T extends HTMLElement>(threshold = 0.15) {
  const ref = useRef<T>(null);
  const [inView, setInView] = useState(false); // stable false on server AND first client render — no hydration mismatch

  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    const observer = new IntersectionObserver(
      ([entry]) => { if (entry.isIntersecting) { setInView(true); observer.disconnect(); } },
      { threshold }
    );
    observer.observe(el);
    return () => observer.disconnect();
  }, [threshold]);

  return { ref, inView };
}
```
Source: general IntersectionObserver + hydration-safety pattern `[CITED: web search — multiple Next.js hydration-error guides]`. The key rule: `inView` starts `false` on both server and client renders — only an effect (which never runs during SSR) can flip it, so there's never a server/client output mismatch.

### Pattern 3: Motion variants for chat-bot message sequencing (D-19–D-24)
**What:** Declarative `variants` + `AnimatePresence` drive the typing-indicator → message-slide-in → quick-reply sequence without manual `setTimeout` animation code.
**Example:**
```tsx
'use client';
import { AnimatePresence, motion } from 'motion/react';

const messageVariants = {
  hidden: { opacity: 0, y: 8 },
  visible: { opacity: 1, y: 0, transition: { duration: 0.25, ease: [0.16, 1, 0.3, 1] } }, // D-20, D-32
};

// Each new message pushed into state renders as:
<AnimatePresence>
  {messages.map((m) => (
    <motion.div key={m.id} variants={messageVariants} initial="hidden" animate="visible">
      {m.text}
    </motion.div>
  ))}
</AnimatePresence>
```
The 300–500ms inter-message delay (D-21) and the typing-dot pulse (D-19) are sequencing/state concerns (still need a `setTimeout`/state-machine to decide *when* to push the next message into the array) — Motion handles the *how it appears*, not the *when*. Source: Motion's documented `variants`/`AnimatePresence` API pattern `[CITED: web search — motion.dev docs referenced in search results]`.

### Anti-Patterns to Avoid
- **Branching initial render on `typeof window !== 'undefined'` or reading `IntersectionObserver`/`matchMedia` results synchronously during render:** causes hydration mismatches — always gate browser-only state behind `useEffect` (see Pattern 2).
- **Importing the entire `@phosphor-icons/react` barrel (`import { X, Y, Z } from '@phosphor-icons/react'` at scale, or a wildcard import) during dev:** can eagerly transpile 9000+ modules and slow dev builds significantly `[CITED: web search]` — import icons by name from the package root (tree-shaking handles it in production builds) and consider `optimizePackageImports: ['@phosphor-icons/react']` in `next.config.js` for dev-time speed.
- **Animating `top`/`left`/`width`/`height` instead of `transform`/`opacity`:** explicitly forbidden by D-38 (perf on low-end devices) — every Motion/CSS animation in this phase must animate only `transform` and `opacity`.
- **Re-theming `packages/ui/styles/theme.css` to "make it easier" to share tokens:** explicitly forbidden by D-01/D-02 — even if it seems like less duplication, it breaks the admin-panel/admin-simulation boundary.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Scroll-triggered fade/translate reveals | A custom scroll-position-polling system, or a full scroll-animation library | Native `IntersectionObserver` in a ~30-line hook (Pattern 2 above) + Motion's `animate`/`variants` for the actual transition | D-44 explicitly requires this — IntersectionObserver is a stable, well-supported native API; a hand-rolled `scroll` event listener with position math would be both worse-performing and explicitly against the decision |
| Message slide-in / typing-dot pulse / quick-reply hover-lift animation primitives | Manual CSS `@keyframes` + imperative class-toggling for each interaction | Motion's `variants`/`animate`/`whileHover` props | Motion already encodes the easing curve (`cubic-bezier(0.16,1,0.3,1)`), exit-animation cleanup on unmount, and gesture (`whileHover`/`whileTap`) support — reimplementing this in raw CSS/JS is exactly the "AI made it decorative, not functional" anti-pattern the ТЗ's D-33 golden rule warns against |
| Icon set | A fully custom SVG icon library drawn from scratch | `@phosphor-icons/react` | D-15 explicitly recommends Phosphor as the default; hand-drawing 20-30 consistent 1.5px-stroke linear icons is high-effort for a marginal design-control gain over an existing, well-executed linear icon family |
| Count-up number animation (D-27, applies to `@repo/ui`-based admin-demo in Phase 2, not this phase) | A custom `requestAnimationFrame` counter loop | Motion's `useMotionValue` + `animate()` (or a small dedicated count-up hook using Motion's `animate` under the hood) | Not this phase's scope (D-02/D-07), but noted for Phase 2 replanning continuity — Motion already ships spring/tween interpolation, no need to hand-roll easing math |

**Key insight:** Every "Don't Hand-Roll" item in this phase traces back to D-33's golden rule (animation must confirm something functional) and D-38 (transform/opacity only, for perf) — using Motion + native IntersectionObserver, rather than hand-rolled equivalents, is the difference between "looks premium" and "looks premium AND performs like it," which is exactly what D-46's Lighthouse ≥85 budget under animation load requires.

## Common Pitfalls

### Pitfall 1: Tailwind v4 token-namespace collision between `@repo/ui` and the new premium tokens
**What goes wrong:** If the new apps/web token names accidentally reuse `@repo/ui`'s existing CSS custom property names (`--primary`, `--background`, `--card`, `--border`, `--muted`, `--accent`, `--ring`, `--chart-1..5`, `--sidebar*`, and Phase 1's `--brand`), Tailwind v4's cascade means whichever `@theme`/`:root` block loads last silently overrides the other — breaking the admin-simulation's `@repo/ui` styling without any build error.
**Why it happens:** Both token sets compile into the same global CSS custom-property namespace (`:root`) unless deliberately prefixed differently.
**How to avoid:** Use a distinct prefix for every new premium token (e.g. `--color-dt-*`/`--radius-dt-*` as in Pattern 1) — never reuse `@repo/ui`'s existing token names, even for conceptually-similar roles (e.g. don't redefine `--primary` to be the new navy).
**Warning signs:** The Demo page's admin-panel simulation (still `@repo/ui`-styled) visually shifts color/shape after this phase ships, even though `packages/ui/styles/theme.css` itself was never edited.

### Pitfall 2: `'use client'` boundary creep pulling Server Components into the client bundle
**What goes wrong:** Wrapping large page sections (rather than small leaf components) in `'use client'` to use Motion/IntersectionObserver drags all their server-renderable children (headings, copy, Phosphor icon markup) into the client JS bundle too, inflating bundle size and directly threatening D-46's Lighthouse budget.
**Why it happens:** It's easier to slap `'use client'` at the top of a whole section component than to carefully split "the part that needs `useInView`/motion" from "the static content inside it."
**How to avoid:** Keep the client boundary at the smallest possible leaf (e.g. a `<Reveal>` wrapper component that receives `children` as a prop from a Server Component parent — Pattern 2's shape) rather than marking entire page sections as client.
**Warning signs:** `next build`'s bundle analysis shows unexpectedly large First Load JS on marketing pages that are mostly static text.

### Pitfall 3: `prefers-reduced-motion` implemented inconsistently across Motion animations vs. hand-written CSS
**What goes wrong:** D-37 requires disabling/simplifying decorative motion (parallax, cursor-reactivity, bounce) under `prefers-reduced-motion: reduce`, but Motion animations and raw CSS `@keyframes`/transition-based hover effects need separate reduced-motion handling — a CSS `@media (prefers-reduced-motion: reduce)` block does NOT automatically disable Motion's JS-driven `animate()` calls.
**Why it happens:** Motion (and most JS animation libraries) don't automatically read the OS-level media query for every animation call unless explicitly wired up.
**How to avoid:** Use Motion's built-in `useReducedMotion()` hook (or check `window.matchMedia('(prefers-reduced-motion: reduce)').matches` inside a `useEffect`, mirroring Pattern 2's SSR-safety shape) to conditionally skip/simplify parallax and cursor-reactivity animations; pair with a global CSS rule (`@media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; } }`) for any remaining CSS-only transitions.
**Warning signs:** Manual testing with OS-level "reduce motion" enabled still shows the hero's magnetic-cursor effect or full-speed parallax.

### Pitfall 4: "Inter Display" font files sourced from an unofficial mirror instead of the official `rsms/inter` release
**What goes wrong:** Because neither Google Fonts nor Fontsource package "Inter Display" directly, a plan or implementer might reach for a third-party font-conversion site or unofficial GitHub fork to get the woff2 files — introducing supply-chain risk and potential license/attribution gaps.
**Why it happens:** The obvious `next/font/google` / `@fontsource/*` shortcuts don't exist for this specific family, creating pressure to find a workaround.
**How to avoid:** Source "Inter Display" woff2 files only from the official `rsms/inter` GitHub repository's Releases page (currently v4.1, OFL-1.1 licensed) — the release archive ships pre-built static woff2 files under the "Inter Display" family name, ready to drop into `next/font/local`.
**Warning signs:** A `next/font/local` `src` pointing at a font file whose provenance isn't traceable to `github.com/rsms/inter/releases`.

### Pitfall 5: Phosphor + Lucide dual-import bloat if not scoped correctly
**What goes wrong:** Both icon libraries end up imported broadly across shared code (rather than Phosphor strictly for new premium UI and Lucide strictly for the `@repo/ui` admin-simulation per D-02), doubling icon-related bundle weight for no design benefit.
**Why it happens:** Convenience — reaching for whichever icon package is already imported in a file, regardless of which "system" that file belongs to.
**How to avoid:** Treat the D-02 boundary as a hard import rule: files under the new premium component tree import only from `@phosphor-icons/react`; only the admin-simulation's `@repo/ui`-based components import from `lucide-react`.
**Warning signs:** A premium marketing-page component importing from `lucide-react`, or vice versa.
