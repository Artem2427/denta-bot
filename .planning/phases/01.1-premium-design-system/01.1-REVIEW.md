# Code Review: Phase 01.1

## Findings

### CR-1
**File:** apps/web/app/layout.tsx:22-34 (esp. line 28) and apps/web/shared/components/header.tsx:36-41
**Severity:** Critical
**Issue:** `Header` renders with `position: fixed` unconditionally (both the scrolled and unscrolled className branches include `fixed top-0 left-0 right-0 z-50`), but `RootLayout`'s `<main>{children}</main>` (and no other file in the shell) reserves any top offset for the header's height (`h-16`/`lg:h-20`). Every page rendered through this layout will have its first ~64–80px of content rendered directly under/behind the floating header. Verified no compensating `pt-16`/`scroll-mt-*`/spacer exists anywhere in `apps/web/app` or `apps/web/shared` (grepped both trees). `not-found.tsx`'s vertically-centered content is one immediate victim, but this affects every future route built on this shell.
**Recommendation:** Add a top padding/margin to `<main>` in `layout.tsx` matching the header's height (`pt-16 lg:pt-20`), or give the header a fixed `h-16 lg:h-20` sibling spacer, so the shell reserves space for the fixed header by construction rather than relying on every future page to compensate individually.

### WR-1
**File:** apps/web/app/premium-theme.css (no `.dark`/`prefers-color-scheme` block for any `--color-dt-*` token) and apps/web/shared/components/theme-toggle.tsx:9-40
**Severity:** Warning
**Issue:** `layout.tsx` wraps the app in `next-themes`' `ThemeProvider attribute="class"`, and `ThemeToggle` toggles between `light`/`dark` by flipping the `.dark` class on `<html>`. `packages/ui/styles/theme.css` does define a `.dark { … }` override block (for its own shadcn tokens), but `premium-theme.css` — which defines every `--color-dt-*` token actually consumed by `Header`, `Footer`, `Logo`, `PremiumButton`, `PremiumCard`, `SignatureMark`, `not-found.tsx`, etc. — defines only one (light) value per token, with no `.dark` or `prefers-color-scheme: dark` override anywhere. Confirmed via grep: zero `dark:`-prefixed Tailwind classes exist anywhere in `apps/web/shared` or `apps/web/app`. Net effect: clicking the theme toggle changes `<html>`'s class but produces no visible change anywhere in the premium marketing UI — it's a fully non-functional control from the user's perspective.
**Recommendation:** Either scope a dark palette for the `dt-*` tokens (mirroring D-05's table with dark-mode equivalents) and add the `.dark` overrides in `premium-theme.css`, or explicitly descope dark-mode support for this milestone and remove/hide `ThemeToggle` from the premium shell until a dark palette exists, so the control isn't shipped in a visibly broken state.

### WR-2
**File:** apps/web/shared/components/header.tsx:56, apps/web/shared/components/footer.tsx:51,59,67,75,92,100,108,128,139
**Severity:** Warning
**Issue:** `text-dt-coral` (#E86B5A) is used as the hover-state text color for nav/footer links on the `dt-warm-white` (#FAFAF8) background. Measured WCAG contrast ratio (relative luminance formula): **3.01:1**, which fails the 4.5:1 AA minimum required for normal-size/-weight text (D-35) — these are `text-sm`/`text-base font-medium` links, not large/bold text that would qualify for the relaxed 3:1 threshold. This pattern repeats across every nav link in the header and every link column in the footer (9 occurrences), so it's a systemic contrast failure, not a one-off.
**Recommendation:** Pick a hover color that clears 4.5:1 against `dt-warm-white` — either darken the coral for text use only (e.g. a darker coral shade reserved for text-on-light contexts) or switch link hover to `dt-navy`/`dt-teal` (teal measures 4.81:1, passing) and reserve literal coral for backgrounds/icons/borders per D-06's "coral for buttons/accents, not large text areas" intent.

### WR-3
**File:** apps/web/shared/components/header.tsx:43, apps/web/shared/components/footer.tsx:13 vs. apps/web/shared/components/container.tsx
**Severity:** Warning
**Issue:** `Header` and `Footer` both hardcode Tailwind's built-in `container mx-auto px-4 lg:px-8` utility class instead of using the `Container` component (`apps/web/shared/components/container.tsx`) that this same phase built specifically to centralize max-width via the `--dt-container-max` (1280px, D-14) token — confirmed via Plan 02's own text: "giving every future page section a consistent max content width without hardcoding the pixel value per-component." No `@utility container` customization exists anywhere in the repo (grepped), so Tailwind v4's default `.container` utility applies its own breakpoint-stepped max-width (matching each breakpoint's min-width, up to 1536px at `2xl`) rather than the flat 1280px cap `Container`/`--dt-container-max` defines. On viewports wider than 1280px, header/footer content will visibly extend wider than every page section that correctly uses `<Container>`, breaking horizontal alignment between the shell and page content, and the max-width logic is now duplicated (differently) in three places instead of one.
**Recommendation:** Replace `<div className="container mx-auto px-4 lg:px-8">` in both `header.tsx` and `footer.tsx` with `<Container>`, matching the primitive this phase already built for exactly this purpose.

### WR-4
**File:** apps/web/shared/components/header.tsx:76-89 (mobile menu toggle button) and apps/web/shared/components/theme-toggle.tsx:17-23 (pre-mount fallback)
**Severity:** Warning
**Issue:** Two icon-only buttons ship with no accessible name. (1) Header's mobile menu toggle renders only a `List`/`X` Phosphor icon inside `PremiumButton`, with no `aria-label`, `aria-expanded`, or `aria-controls` — a screen reader announces just "button" with no indication of purpose or open/closed state. (2) `ThemeToggle`'s `!mounted` fallback (rendered during SSR/first paint, before `next-themes` hydrates) renders only a `Sun` icon with no `sr-only` text or `aria-label` — the mounted branch does add `<span className="sr-only">Перемкнути тему</span>`, but the pre-mount fallback branch does not, so there's a brief window (and any environment where JS hydration is delayed) where the control has zero accessible name.
**Recommendation:** Add `aria-label="Відкрити меню"/"Закрити меню"` + `aria-expanded={isMobileMenuOpen}` to the header's mobile toggle button, and add the same `sr-only` label text (or an `aria-label`) to `ThemeToggle`'s pre-mount fallback so it's never rendered without an accessible name.

### WR-5
**File:** apps/web/shared/components/header.tsx:93-138
**Severity:** Warning
**Issue:** The mobile nav's `AnimatePresence`/`motion.div` (height/opacity animation on menu open/close) does not check `useReducedMotion()`, unlike `Reveal` (`apps/web/shared/components/reveal.tsx:19,26-29`), which correctly branches to a no-motion variant when the user has `prefers-reduced-motion: reduce` set. This matters because `premium-theme.css`'s global `@media (prefers-reduced-motion: reduce)` rule (lines 66-75) only zeroes CSS `animation-duration`/`transition-duration`, which has no effect on Motion-library-driven animations — Motion (`motion/react`) animates via inline styles/WAAPI, not CSS `transition`, so this one animated element in the shell is left un-gated and will still animate for users who've opted out (violates D-37).
**Recommendation:** Wrap the mobile menu's motion variants the same way `Reveal` does — check `useReducedMotion()` and swap to an instant/opacity-only transition when true (or wrap the app in Motion's `<MotionConfig reducedMotion="user">` globally in `layout.tsx` so every current and future `motion.*` usage is covered by one guard instead of per-component).

### IN-1
**File:** apps/web/shared/components/premium-button.tsx:12
**Severity:** Info
**Issue:** The `coral` button variant (`bg-dt-coral text-dt-navy`) measures **4.586:1** contrast — technically clears the 4.5:1 AA minimum (D-35) but by only a 0.086 margin, for `text-sm font-medium` (500-weight) text that doesn't qualify as "large text" under WCAG's relaxed 3:1 threshold. This is the site's primary CTA button (used in header, footer, hero, not-found), so it's worth a comfortable margin rather than a hairline pass that could tip below 4.5:1 with minor font-rendering/anti-aliasing variance across browsers/OSes.
**Recommendation:** Consider a marginally darker coral or navy-on-coral adjustment to build in headroom (e.g. targeting ≥5:1), or explicitly accept the current margin as sufficient — no code change required if the team is fine with the current margin.
