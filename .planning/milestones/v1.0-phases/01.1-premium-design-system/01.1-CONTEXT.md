# Phase 01.1: Premium Design System (apps/web) - Context

**Gathered:** 2026-08-08
**Status:** Ready for planning
**Source:** PRD Express Path (.planning/phases/01.1-premium-design-system/01.1-PRD.md)

<domain>
## Phase Boundary

Establish a bespoke premium visual system for the `apps/web` marketing site — its own color palette, typography scale, spacing/radius/shadow language, motion/animation primitives, and icon system — replacing Phase 1's brand-blue `@repo/ui`-based theme on marketing pages. Retrofit Phase 1's already-shipped shell (header, footer, logo, theme-toggle) to the new system. Scoped to `apps/web` only: `packages/ui` (`@repo/ui`) is **not** modified and is **not** the foundation for this new system — it remains exactly as Phase 1 left it, since it's still the base for `apps/admin-panel` and for the Demo page's embedded admin-panel simulation (built later, in Phase 2/replan).

This phase does not build any page content (Home/Contacts/Demo/Prices/Blog) — it builds the design-system layer (tokens, primitive components, motion utilities, icon set) that those pages will consume once replanned. Requirements covered: DESIGN-01, DESIGN-02, DESIGN-03 (see `.planning/REQUIREMENTS.md`).

</domain>

<decisions>
## Implementation Decisions

### Scope Boundary (locked, user-directed — read this first)

- **D-01:** The premium redesign applies to `apps/web` only. It is explicitly **not** based on `packages/ui` — do not build it by re-theming `@repo/ui`'s existing tokens/components.
- **D-02:** Exception: the Demo page's embedded admin-panel simulation (dashboard/calendar/analytics mockup inside `/demo`'s "Admin" tab) stays on `@repo/ui` components, unmodified, because it represents the real `apps/admin-panel` product. This phase must not touch `packages/ui/styles/theme.css` or `packages/ui/src/components/*`.
- **D-03:** New premium components live under `apps/web/shared/components/` (per the folder convention from Phase 2 planning: `app/`=routes only, `modules/<page>/`=page-specific, `shared/`=cross-page code) — not in `packages/ui/src/components/`.
- **D-04:** Phase 1's shipped shell (`apps/web/shared/components/{header,footer,logo,theme-toggle}.tsx`, currently built on `@repo/ui` Button/etc. with the `#1d6be4` brand-blue token) is in scope to be rebuilt against the new premium system, since header/footer are part of "the site."

### Color Palette

- **D-05:** New token set (apps/web-scoped, NOT written into `packages/ui/styles/theme.css`):

| Role | Name | Hex | Usage |
|---|---|---|---|
| Primary dark | Deep navy | `#1A2B3D` | Headings, hero background, text on light |
| Trust accent | Teal | `#2C7A7B` | Icons, lines, secondary accents, charts |
| Background | Warm white | `#FAFAF8` | Main page background (warmer than `#FFFFFF`) |
| Action accent | Coral | `#E86B5A` | CTA buttons, active chat-bot elements, signature detail |
| Text | Graphite | `#2D3436` | Body text, softer than pure black |
| Success (admin-demo only) | Sage | `#7A9E7E` | Confirmations, "available" status |
| Warning (admin-demo only) | Amber muted | `#D4A24C` | "pending confirmation" status |

- **D-06:** Coral is reserved for action/live-moment emphasis only (buttons, a just-arrived bot message, a confirmation) — never as a large-area background. Its value is in rarity.
- **D-07:** Sage/Amber are scoped to the admin-panel-simulation's status coloring per the original ТЗ — but per D-02, the admin-simulation itself renders via `@repo/ui`. Claude's Discretion (below) covers how literally these two colors map onto that constraint.

### Typography

- **D-08:** Headings: geometric sans-serif with character — Söhne, General Sans, Inter Display, or Neue Montreal (no serif). Body: same or related family (Inter, Söhne Buch). Higher-than-usual weight contrast between heading (600–700) and body (400) so hierarchy reads instantly.
- **D-09:** Size scale (rem): H1 3.5–4.5 (hero), H2 2.25–2.75 (sections), H3 1.5 (card subheads), Body 1–1.125, Caption/label 0.8125 with `+0.02em` letter-spacing, uppercase for status labels.
- **D-10:** Line-height: 1.5 for body text, 1.1–1.2 for headings.

### Grid, Space, Shape

- **D-11:** Generous whitespace; restraint over "shouting."
- **D-12:** Radius: 8–12px for cards/buttons, 6px for inputs. No pill/capsule shapes — reduces perceived seriousness.
- **D-13:** Shadows: soft, layered (2–3 stacked shadows of varying blur instead of one hard `box-shadow`).
- **D-14:** 12-column grid, max content width 1200–1280px, generous inter-section spacing (96–140px desktop).

### Iconography & Imagery

- **D-15:** Linear icons, 1.5px stroke, one consistent style site-wide (Phosphor Icons recommended, or a custom set — not Font Awesome or mixed default packs).
- **D-16:** No dominant tooth/cross iconography (reads as cheap, duplicates competitors).
- **D-17:** Bot/admin interface screenshots must show realistic data (plausible names, time slots) — no lorem ipsum, no abstract 3D-blob illustrations. Illustrative elements, if needed, are thin linear diagrams (medical-schema style), not cartoon characters.

### Chat-Bot Demo — Interaction Spec

- **D-18:** Realistic messenger UI (Telegram/iMessage reference): correctly-spaced bubbles, timestamp under each message, delivered/read status on user messages.
- **D-19:** Typing indicator before bot reply: 3 dots pulsing in sequence (`opacity` 0.3→1→0.3, 200ms stagger).
- **D-20:** Message appearance: slide-in from below (`translateY` 8px→0, opacity 0→1), 250ms, easing `cubic-bezier(0.16, 1, 0.3, 1)`.
- **D-21:** 300–500ms delay between sequential messages (paces like a real conversation, not all-at-once).
- **D-22:** Quick-reply buttons appear after the bot's reply, coral outline, subtle hover-lift.
- **D-23:** Auto-scroll to new messages is smooth, never an instant jump.
- **D-24:** Demo script shows a real use-case end-to-end (book appointment → choose doctor → choose time → confirm → reminder) — the functionality sells itself without marketing copy.

### Admin-Panel Demo — Interaction Spec (behavior only; see D-02 for styling boundary)

- **D-25:** Interactive mockup, not a static screenshot — clickable calendar dates, hover states on appointment cards, even if functionally limited.
- **D-26:** Components to demonstrate: color-coded appointment calendar (sage/coral/amber statuses), patient card on click (name, visit history, notes), analytics block (room utilization, weekly appointment count).
- **D-27:** Animation timing (applies to whatever `@repo/ui`-based implementation Phase 2 builds, per D-02): analytics counters count up 0→final over 800–1200ms ease-out; bar charts grow bottom-up, staggered 80ms per bar; tab switches fade (150ms), not instant; calendar-entry hover = lift + tooltip, 150ms.

### Site-Wide Animation System

- **D-28:** Scroll-triggered reveals: fade + `translateY(20px→0)` on viewport entry (Intersection Observer, threshold ~0.15). Elements within a section stagger 60–100ms apart, not simultaneous.
- **D-29:** Parallax: light, hero-section only — background elements move at 20–30% of scroll speed relative to foreground.
- **D-30:** Hover micro-interactions: cards `translateY(-4px)` + stronger shadow, 200ms (avoid `scale()` — reads cheaper). Buttons: background-color change + slight lift, no bounce.
- **D-31:** Optional cursor-reactivity, hero only: one decorative element with a subtle magnetic-cursor offset (8–15px amplitude).
- **D-32:** Easing everywhere: `cubic-bezier(0.16, 1, 0.3, 1)` ("expo-out"), never linear.
- **D-33:** Golden rule: every animation must *confirm* something (bot typing → reply forming; chart growing → data is real), never pure decoration.

### Signature Detail

- **D-34:** One recurring element site-wide: a thin coral mark/dot appearing exactly at moments of "action" (new bot message, booking confirmed, active admin-demo status). Disciplined to interaction points only, not scattered decoratively — this is the product's visual signature.

### Accessibility & Performance

- **D-35:** Text contrast ≥ WCAG AA (4.5:1 body text).
- **D-36:** Visible `focus-visible` state on all interactive elements (not just removing the outline).
- **D-37:** `prefers-reduced-motion: reduce` disables or simplifies-to-fade all decorative animation (parallax, cursor-reactivity, bounce).
- **D-38:** Animations run on `transform`/`opacity` only (not `top`/`left`/`width`) for low-end-device performance.
- **D-39:** Heavy demo blocks (chat-bot, admin-demo) lazy-load — must not block first page paint.

### Mobile

- **D-40:** Chat-bot demo on mobile: same animation quality as desktop, not a simplified version.
- **D-41:** Admin-demo on mobile: acceptable to present as a vertical-scroll preview with explanatory copy instead of forcing a full dashboard into a small viewport.
- **D-42:** "Request a demo" CTA is sticky or otherwise always within easy reach on mobile.

### Technical Implementation

- **D-43:** Framer Motion or GSAP for scroll-reveals and the chat-bot's animation sequencing.
- **D-44:** Intersection Observer API for scroll-triggered animation, avoid heavy scroll-animation libraries beyond the chosen motion library.
- **D-45:** Fonts self-hosted (woff2) — no third-party CDN dependency for critical rendering.
- **D-46:** Target Lighthouse Performance ≥85 even with animations active.

### Acceptance Checklist (from ТЗ §14 — carries into this phase's must_haves)

- No element reads as an uncustomized default Bootstrap/Tailwind component.
- The chat-bot demo looks like a real working product, not a picture labeled "demo."
- No animation is purely decorative without functional meaning.
- Palette applied consistently; coral used sparingly, action-only.
- Typographic hierarchy reads instantly, no effortful parsing.
- Site is equally strong on mobile, not a "cut-down" desktop version.
- First impression (hero, first 3 seconds) reads at a Linear/Stripe/Intercom level.

### Claude's Discretion

- Exact font pick among Söhne/General Sans/Inter Display/Neue Montreal — several are commercial/licensed (Söhne, General Sans, Neue Montreal); pick a self-hostable option consistent with D-45 (Inter Display is free/self-hostable via Google Fonts or Fontsource and is explicitly listed as an acceptable choice in D-08). Flag the licensing constraint explicitly in the plan.
- Framer Motion vs. GSAP (D-43) — pick based on bundle size / Next.js App Router (RSC) compatibility; Framer Motion (`motion/react`) is the more common Next.js App Router pairing.
- Exact icon package for D-15 (`@phosphor-icons/react` vs. a hand-picked custom SVG set) — Phosphor's official React package is a reasonable default; note that `lucide-react` (already an `apps/web` dependency from Phase 1) stays in use for the Demo page's `@repo/ui`-based admin-simulation only, per D-02.
- How D-07's sage/amber admin-demo status colors reconcile with D-02 (admin-demo stays `@repo/ui`-styled) — e.g., whether these become new `@repo/ui` Badge/status variants (following the existing "extend `@repo/ui` with variants" pattern from Phase 1) is a Phase 2-replan decision, not this phase's — this phase only needs to define the two hex values for later reference.
- Exact magnetic-cursor implementation for D-31 (raw `mousemove` listener vs. a motion-library helper) — optional/hero-only, low-risk either way.
- Breakpoint(s) for D-41's mobile admin-demo vertical-scroll-preview treatment — standard Tailwind `md`/`lg` breakpoints already in use are a reasonable default.

</decisions>
