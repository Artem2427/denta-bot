# Phase 06.1: Premium Visual Restyle (apps/web) - Context

**Gathered:** 2026-08-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Purely visual/CSS restyle of the `apps/web` marketing site (Home, /prices, /demo, /blog, /blog/[slug], /contacts) to look premium and expensive, and to sell trial signups. `apps/web` already runs Phase 01.1's bespoke `dt-` premium design system (own tokens in `apps/web/app/premium-theme.css`, own components in `apps/web/shared/components/`) — this phase **extends and tightens that existing system**, it does not replace it or build a new one.

No route changes, no component prop/API changes, no server logic changes, no form field changes, no copy changes (Ukrainian text stays verbatim — only line-break/alignment adjustments allowed), no new npm dependencies, no changes to `packages/ui`/`packages/ui/styles/theme.css` (that stays the source of truth only for `apps/admin-panel`/`apps/platform-admin` and the Demo page's embedded admin-simulation tab, untouched by this phase).

</domain>

<decisions>
## Implementation Decisions

### Typography — font swap (hard constraint conflict found during context-gathering)
- **D-01:** Current heading/body font is plain Google-Fonts **Inter** (`apps/web/app/fonts.ts`, bound to `--font-dt-heading-raw`/`--font-dt-body-raw` via `next/font/google`), which the client's brief explicitly excludes ("без Inter/Roboto/Fraunces"). Client chose **Manrope** as the replacement, confirmed live during this planning session. Swap both `interHeading`/`interBody` exports in `apps/web/app/fonts.ts` to `Manrope` (same two-weight-bucket pattern: 700/800 for heading register, 400/500 for body register), `subsets: ['latin', 'cyrillic']` (Ukrainian copy), `display: 'swap'`. This is a `next/font/google` swap only — no new package. — **Reversibility:** costly (touches every rendered page's typography) — already user-confirmed, do not re-litigate.
- **D-02:** Add a third type register — monospace for eyebrow labels / KPI numbers / prices — via `next/font/google`'s **JetBrains Mono** (confirmed Cyrillic support, ubiquitous "technical/premium" association, zero manual asset vendoring). New export `jetbrainsMono` in `fonts.ts`, weight `['500']`, `variable: '--font-dt-mono-raw'`, bound to a new `--font-dt-mono` token in `premium-theme.css`'s `@theme inline` block (mirrors the existing heading/body binding pattern). Register the new CSS variable on the root layout's `className` alongside the existing two font variables (`apps/web/app/layout.tsx`).

### New `dt-` design tokens (apps/web/app/premium-theme.css — additive only, D-03..D-09)
- **D-03:** Spacing scale tokens `--spacing-dt-{4,8,12,16,24,32,48,64,96,112}` (px values, e.g. `--spacing-dt-4: 0.25rem` ... `--spacing-dt-112: 7rem`) added to `@theme` so Tailwind generates `p-dt-24`, `gap-dt-16`, etc. utilities. Existing arbitrary-value spacing sprinkled through pages should migrate to these where it lines up with the scale; do not force-fit values that don't match (e.g. an existing intentional `gap-3` can stay if 12px isn't meaningfully different from scale intent — planner/executor discretion on a per-occurrence basis, not a mechanical find-replace).
- **D-04:** `--dt-border` token (not a Tailwind color — a raw CSS custom property, matches existing `--dt-container-max`/`--dt-ease-expo-out` pattern in the `:root` block) = `rgba(26, 43, 61, 0.08)` — the canonical hairline border. `PremiumCard`'s current `border-dt-navy/10` (≈0.1 alpha) should tighten to reference this exact hairline value (via an arbitrary-value utility `border-[var(--dt-border)]` or a new `--color-dt-hairline` @theme color token — planner's choice of mechanism, but the resolved alpha must be exactly `.08` everywhere hairline borders appear, not `.10`).
- **D-05:** `--dt-ring` token = teal focus ring color reference for custom `focus-visible` styling (buttons/inputs currently ring `dt-navy` per `premium-button.tsx` — brief calls for teal focus rings specifically; migrate focus-visible rings from navy to teal via this token).
- **D-06:** `--dt-duration-fast` = `180ms`, `--dt-duration-base` = `240ms` (within brief's 180–260ms band). `--dt-ease-expo-out` **already exists** in `:root` (`cubic-bezier(0.16, 1, 0.3, 1)`) and already exactly matches the brief's spec — reuse as-is, do not duplicate.
- **D-07:** `--text-dt-eyebrow` type-level token (uppercase, `0.8125rem`, `letter-spacing: 0.02em`, bound to `--font-dt-mono`) — formalizes the existing ad-hoc `.dt-caption` utility class into a proper `@theme` text token following the same pattern as `--text-dt-h1`/`--text-dt-h2`/etc. The existing `.dt-caption` utility class can be deprecated in favor of this once all call sites migrate (grep for `dt-caption` usage first — planner should enumerate call sites).
- **D-08:** Radius tokens (`--radius-dt-card: 0.625rem` / 10px, `--radius-dt-input: 0.375rem` / 6px) and shadow tokens (`--shadow-dt-sm/card/hover`) **already exist and already match the brief's spec exactly** (navy-tinted, layered, no pure black, no 20px+ radii). No new radius/shadow tokens needed — audit call sites for any stray hardcoded radius (found: 2 occurrences of `rounded-[` arbitrary values sitewide — planner should locate and convert these to the existing `rounded-dt-card`/`rounded-dt-input` tokens) and any inline box-shadow not using `var(--shadow-dt-*)`.
- **D-09:** No hardcoded hex colors exist in `apps/web/app|modules|shared` today (verified via grep — Phase 01.1-03 already established clean `dt-` token discipline). This phase's "remove hardcoded hex" acceptance criterion is already satisfied; treat it as a regression guard during the restyle (don't introduce new hex literals while touching files), not a cleanup backlog.

### New shared primitives (apps/web/shared/components/ — additive, follow existing CVA pattern)
- **D-10:** Existing primitives to **reuse/extend in place** (do not fork parallel new components): `Container` (`container.tsx` — already correct, `max-w-[var(--dt-container-max)]`), `PremiumButton` (`premium-button.tsx` — CVA-based, extend not replace), `PremiumCard` (`premium-card.tsx` — extend not replace), `Reveal` (`reveal.tsx` — motion wrapper, already has `useReducedMotion()` + `useInView`, extend not replace).
- **D-11:** New primitives to create in `apps/web/shared/components/` (none of these exist yet — confirmed via directory listing): **`Section`** (semantic `<section>` wrapper providing the `clamp(64px, 8vw, 112px)` vertical rhythm + optional `tone` variant for `warm-white` vs `navy` background surfaces — CVA `tone` variant, not ad-hoc className per page), **`Eyebrow`** (small uppercase mono label component using the new `--text-dt-eyebrow` token, optional `tone` variant for use on navy backgrounds), **`SectionHeading`** (composes `Eyebrow` + `h2`/`balance` heading + optional subtext paragraph with `text-wrap: pretty` + `max-w` line-length clamp — the single recurring header pattern currently duplicated per-page), **`Stat`** (KPI/number display with `tabular-nums`, mono/eyebrow label under or beside the number — used for hero stats, pricing numbers, any KPI callouts).
- **D-12:** Naming: new primitives are plain names (`Section`, `Eyebrow`, `SectionHeading`, `Stat`) — no `Premium` prefix — since `PremiumButton`/`PremiumCard`/`PremiumBadge`/etc. established that prefix specifically for the Phase 01.1-era component set; the brief's own primitive list (`Section, Container, Eyebrow, SectionHeading, Card, Stat, Button`) uses bare names. Do not rename existing `Premium*` components — new primitives sit alongside them. Planner's discretion whether `Card`/`Button` in the brief's list refer to the existing `PremiumCard`/`PremiumButton` (recommended reading) or need bare-named wrapper aliases — default assumption is **no aliasing**, existing `Premium*` names stay as the canonical Card/Button primitives referenced by the brief.

### Button spec alignment (D-13)
- **D-13:** `PremiumButton`'s `coral` variant needs: font-weight 800 (currently `font-medium` ≈500 — brief wants 800), `box-shadow: 0 8px 16px rgba(232,107,90,.28)` (currently none), hover darkens 6% (currently `hover:bg-dt-coral/90` — opacity-based, not a true darken; acceptable interpretation unless planner finds a token-based darken alternative), min-height 48px (currently `h-10`/40px on `default` size — brief requires ≥48px default, ≥44px minimum on mobile). `outline` variant (brief's "Secondary: біла з hairline-межею") should reference the new `--dt-border` hairline token per D-04 rather than `border-dt-navy` at full opacity.

### Motion tuning (D-14 — apps/web/shared/lib/motion.ts, existing file)
- **D-14:** Current `revealVariants` uses `y: 20`, `duration: 0.5` (500ms) — brief specifies `translateY(14px)`, 180-260ms. Update `revealVariants`/`revealContainerVariants` constants in place: `y: 14`, `duration: 0.2` (200ms, within band), `EASE_DT_EXPO_OUT` already correct — reuse. `revealContainerVariants`'s `staggerChildren: 0.08` → `0.06` (brief's "stagger 60ms"). These are shared constants — updating them retunes every `Reveal`-wrapped section sitewide, which is the intent (site-wide motion consistency is explicitly called for). `idleBounceAnimate`/`idleBounceTransition` (infinite loop, used on a hero notification card per prior SUMMARY.md history) is the brief's explicit exception ("виняток — logo marquee") — **the existing idle-bounce use case is NOT a logo marquee**, flag this as a decision point for planning: either treat existing idle-bounce as acceptable (pre-existing, subtle, not the aggressive kind the brief warns against) or remove it. Recommend keeping it (already ships with `useReducedMotion()` gating per Phase 02 history) but planner/executor should surface this explicitly rather than silently deciding either way.

### Header (D-15)
- **D-15:** Current `Header` (`shared/components/header.tsx`) is already sticky (`fixed top-0`) with conditional `bg-dt-warm-white/80 backdrop-blur-md` on scroll, and already has a burger-menu breakpoint (need planner/researcher to confirm exact breakpoint — brief wants `<1024px`). Adjustments needed to hit brief spec exactly: background opacity `.80` → `.86` (`bg-dt-warm-white/[0.86]` or an arbitrary rgba value), `backdrop-blur-md` (12px) → `backdrop-blur-[14px]` (brief's exact 14px), add a hairline bottom border (`border-b border-[var(--dt-border)]`) that's currently absent, and confirm/adjust the CTA-shrinks-on-mobile behavior.

### Screenshot framing (D-16)
- **D-16:** Brief requires bot/admin screenshots framed in iPhone/browser chrome with realistic shadow + soft gradient halo behind, no 3D tilts. Researcher should locate every screenshot/mockup image currently rendered on Home and Demo pages and report their current treatment (raw `<img>`? Already framed? 3D-transformed?) so the planner can scope exact frame-component work — this wasn't inventoried during context-gathering.

### Page-level primitive adoption (D-17)
- **D-17:** Sweep all 5 routes (`app/page.tsx` [home], `app/prices/page.tsx`, `app/demo/page.tsx`, `app/blog/page.tsx`, `app/blog/[slug]/page.tsx`, `app/contacts/page.tsx`) and their `modules/{home,prices,demo,blog,contacts}/` section components, replacing duplicated section-wrapper/eyebrow/heading markup with the new `Section`/`Eyebrow`/`SectionHeading`/`Stat` primitives from D-11, without changing any rendered copy. This is the bulk of the phase's file-touch surface — researcher should enumerate the actual section components per module so planning can size/sequence the sweep (likely multiple plans/waves given ~5 pages × multiple sections each).

### Coral usage discipline (D-18)
- **D-18:** Brief's "no more than two coral elements in viewport at once" is a per-page visual-judgment constraint, not a mechanical rule the code can enforce. Flag it as an explicit review checkpoint during execution/verification (e.g. screenshot each page at each breakpoint and count coral elements in the primary viewport) rather than something the planner encodes as a task precondition.

### Resolutions to RESEARCH.md's open questions (2026-08-18, post-research)

RESEARCH.md (`.planning/phases/06.1-.../06.1-RESEARCH.md`) surfaced 3 open questions plus several pitfalls needing an explicit call. Resolved here so the planner has locked answers, not open items:

- **D-19 (Section `muted` tone):** Add a third `Section` tone, `muted` (`bg-dt-navy/5`), alongside `warm-white`/`navy` from D-11. Confirmed by research: `comparison-table.tsx`, `app/prices/page.tsx`'s FAQ section, and `app/contacts/page.tsx`'s FAQ section all already use the exact identical `bg-dt-navy/5 py-8 lg:py-12` string — a clean DRY target, doesn't contradict D-11 (which named a minimum, not a maximum).
- **D-20 (PremiumButton `icon` size):** Bump `icon` size from `size-10` (40px) to `size-11` (44px) to meet the brief's mobile 44px minimum touch target. Applies site-wide (header's mobile burger toggle is the live use case) — the 44px minimum is a general accessibility floor, not scoped only to `coral`/`outline` CTA variants.
- **D-21 (10 hardcoded non-`dt-` Tailwind palette colors — Pitfall 1/Assumption A5):** Partial fold into the D-17 sweep. Migrate `contact-info.tsx`'s green/blue/purple icon-chip colors and `problem.tsx`'s red/orange/yellow/purple icon-background colors to `dt-` tokens (map each to the nearest semantic `dt-` color at reduced opacity, e.g. `bg-dt-teal/10 text-dt-teal`, `bg-dt-coral/10 text-dt-coral`, `bg-dt-amber/10 text-dt-amber`, `bg-dt-sage/10 text-dt-sage` — planner's exact mapping, staying within the fixed 7-color palette). Leave `testimonials.tsx`'s `text-yellow-400` star-rating color and `bot-tab.tsx`'s `bg-gray-900` phone-bezel color **as-is** — both are "real-world" semantic colors (star ratings are conventionally yellow; phone bezels are conventionally black) with no defensible `dt-` palette equivalent, not chrome inconsistencies.
- **D-22 (phone-frame radius tokens — D-08 follow-up):** The brief's acceptance criterion "тільки токени" (only tokens, no hardcoded px-radii) reads as literal — `bot-tab.tsx`'s 2 arbitrary values (`rounded-[3rem]`, `rounded-[2.5rem]`) should become 2 new dedicated tokens rather than staying arbitrary, since they don't fit the existing `--radius-dt-card`(10px)/`--radius-dt-input`(6px) scale (real phone-bezel radii are much larger by nature). Add `--radius-dt-frame: 3rem` and `--radius-dt-frame-inner: 2.5rem` to `premium-theme.css`, use `rounded-dt-frame`/`rounded-dt-frame-inner` at the 2 call sites.
- **D-23 (phone-frame shadow token):** `bot-tab.tsx`'s `shadow-2xl` (plain Tailwind, not a `dt-` token) should route through an existing or new `--shadow-dt-*` token per the brief's "тіні тільки з --shadow-dt-*" rule — `var(--shadow-dt-hover)` (the existing heaviest tier) is the default recommendation; planner may add a dedicated `--shadow-dt-frame` only if `-hover`'s weight looks visually wrong against the phone bezel.
- **D-24 (input border alpha — D-04 follow-up):** `PremiumInput`/`PremiumTextarea`'s `border-dt-navy/20` (visible functional form-field border, not a decorative hairline) stays at `/20` — **not** migrated to the new `.08`-alpha `--dt-border` hairline token from D-04. Confirmed distinct use case (research's own recommendation): form inputs need a more visible border than card/list hairlines.
- **D-25 (Home hero Unsplash stock photo — D-16 follow-up):** Out of scope. Replacing the stock photo with a real product screenshot is a content/copy decision, and the phase boundary explicitly excludes copy changes. Leave the existing `<Image>` as-is (it already correctly uses `rounded-dt-card`/`shadow-[var(--shadow-dt-card)]`); D-16's "frame it like an iPhone/browser" instruction doesn't apply here since there is no raw screenshot anywhere in the codebase to frame — `bot-tab.tsx`'s phone mockup already has hand-built frame chrome (addressed by D-22/D-23 above), which fully satisfies D-16's intent.
- **D-26 (idle-bounce animation — D-14 follow-up):** Keep `hero.tsx`'s single idle-bounce notification card as-is (already `useReducedMotion()`-gated, subtle, not the "aggressive infinite loop" the brief warns against). Not a logo marquee, but not the kind of motion the brief's exception clause is guarding against either — a considered keep, not a silent one.
