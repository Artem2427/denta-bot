## Summary

This phase extends an already-solid, already-token-disciplined design system (`apps/web/app/premium-theme.css` + `apps/web/shared/components/*`, from Phase 01.1) rather than building anything new. Every one of the CONTEXT.md's numbered decisions (D-01 through D-18) was checked directly against the live source files in this session — the CONTEXT.md's factual claims about current state (`revealVariants` values, `PremiumCard`'s border alpha, the header's breakpoint, the `rounded-[` count) all verified exactly as stated, with one material correction: **D-09's "no hardcoded hex colors" claim is true but incomplete** — there are 10 hardcoded non-`dt-` Tailwind palette color utilities (`bg-green-50`, `text-yellow-400`, `bg-red-100`, etc.) across `contact-info.tsx`, `problem.tsx`, and `testimonials.tsx` that don't route through the `dt-` token system, even though they aren't hex literals. This should be surfaced to the planner as a borderline in-scope cleanup item (see Common Pitfalls).

The bulk of the phase (D-17's page sweep) touches ~20 module files across 5 route trees, replacing a duplicated `<div className="mb-12 text-center"><h2>...</h2></div>` heading pattern (found in 9 of the ~16 section-level blocks) with the new `SectionHeading` primitive, and wrapping bare `<section className="py-8 lg:py-12">` blocks with the new `Section` primitive. Three KPI/number displays are clear `Stat` primitive candidates (hero stats, pricing plan prices). The Demo page's bot phone-mockup (`bot-tab.tsx`) is the only screenshot-adjacent element needing frame work, and it already has device-frame chrome (not a raw `<img>`) — it just needs its 2 hardcoded `rounded-[...]` values converted to `dt-` radius tokens and its `bg-gray-900`/`shadow-2xl` colors converted to `dt-` equivalents. No 3D transforms/rotations exist anywhere in the codebase today (only an accordion chevron's flat `rotate-180`), so D-16's "remove 3D tilts" instruction has nothing to remove — it's a forward-looking constraint, not a fix.

**Primary recommendation:** Treat this as two workstreams that can be sequenced independently: (1) token/primitive foundation work (fonts, new `@theme` tokens, `Section`/`Eyebrow`/`SectionHeading`/`Stat` components, `PremiumButton`/`PremiumCard`/`Reveal`/`Header` retrofits) landing first as its own plan/wave, then (2) the mechanical D-17 page sweep consuming those primitives across the 5 route trees, sized as 2-3 plans (Home is the largest at 7 sections; Prices/Demo/Blog/Contacts can share a plan or two).

### Anti-Patterns to Avoid
- **Hardcoded non-`dt-` Tailwind palette colors:** `bg-green-50`/`text-green-600`, `bg-blue-50`/`text-blue-600`, `bg-purple-50`/`text-purple-600` (`contact-info.tsx`), `bg-red-100`/`bg-orange-100`/`bg-yellow-100`/`bg-purple-100` (`problem.tsx`), `text-yellow-400` ×5 (`testimonials.tsx` star rating). None are hex literals (D-09's grep is technically clean) but all bypass the `dt-` token system. See Common Pitfalls.
- **Bare hardcoded phone-frame chrome:** `bot-tab.tsx`'s `rounded-[3rem] bg-gray-900 p-3 shadow-2xl` / `rounded-[2.5rem]` inner — Tailwind-default gray/shadow, not `dt-` tokens, and the 2 arbitrary-radius values D-08 flags. Convert to `dt-` radius/shadow tokens; `bg-gray-900` (near-black phone bezel) has no direct `dt-navy` equivalent (navy is `#1a2b3d`, lighter than near-black `gray-900` `#111827`) — planner's call whether to keep a deliberately near-black bezel (real phones are black) or map to `dt-navy` for palette discipline. Recommend keeping a dedicated near-black bezel color (phone bezels being black is realistic, not a "premium" violation) but converting the *radius* and *shadow* to `dt-` tokens.

## Common Pitfalls

### Pitfall 1: D-09's "no hardcoded hex" is true but the underlying intent (full token discipline) is not fully met
**What goes wrong:** A planner reading D-09 verbatim ("already satisfied, treat as regression guard") could skip auditing non-hex hardcoded colors entirely, since the CONTEXT.md's own grep only checked for hex literals.
**Why it happens:** `bg-green-50`, `text-yellow-400`, etc. are Tailwind's built-in named palette utilities, not hex strings — a hex-only grep misses them entirely.
**How to avoid:** Confirmed via this session's grep (`grep -rnoE "(bg|text|border)-(red|orange|yellow|green|blue|purple|...)-[0-9]+"`) — exactly 10 occurrences across 3 files: `modules/contacts/contact-info.tsx` (6: green-50/600, blue-50/600, purple-50/600 — the "benefits" icon chips), `modules/home/problem.tsx` (4: red-100/orange-100/yellow-100/purple-100 — the "problem" icon backgrounds), `modules/home/testimonials.tsx` (5: `text-yellow-400` ×5 — star icons). `bg-gray-900` in `bot-tab.tsx` (phone bezel) is a 4th file/case, separately flagged as an anti-pattern above (arguably acceptable to keep since it's a "black phone bezel" realism choice, not a UI-chrome color).
**Warning signs:** Grepping only for `#[0-9a-f]{3,8}` or `rgb(`/`rgba(` hex/rgb literals and declaring the sweep done.
**Recommendation:** Planner's discretion whether to fold these into the D-17 sweep (map to nearest `dt-` semantic — e.g. `bg-dt-teal/10`+`text-dt-teal` could plausibly replace the green "success" chip) or explicitly descope as "decorative accent colors, not chrome" and leave as-is. Either is defensible; leaving it undecided is not — CONTEXT.md's D-09 language could mislead an executor into believing there's nothing left to check.

### Pitfall 2: Two different tokens are both colloquially "the caption token" — don't conflate them during the D-07 migration
**What goes wrong:** D-07 talks about deprecating the `.dt-caption` **utility class** (`@layer utilities { .dt-caption { ... } }`, uppercase+letter-spacing only, no font-size) in favor of the new `--text-dt-eyebrow` **type token**. But there is a *separate*, already-existing `--text-dt-caption` **type-scale token** (`0.8125rem`, defined in the `@theme` block, generates the `text-dt-caption` Tailwind utility) that is a different thing with a confusingly similar name.
**Why it happens:** `.dt-caption` (class) vs `text-dt-caption` (Tailwind utility from `--text-dt-caption`) look almost identical in a `className` string and both relate to "caption" text — easy to grep for one and accidentally touch the other.
**How to avoid:** Verified via this session's grep — exactly 3 sitewide usages of the literal `.dt-caption` class (D-07's actual migration target): `app/demo/page.tsx:13` (`dt-caption mb-4 inline-block rounded-full bg-dt-coral/10 px-3 py-1 text-dt-coral` — the "DEMO MODE" badge) and `modules/demo/bot-tab.tsx:169-170` (chat timestamp row — this one uses `text-dt-caption` the *type-scale token*, not `.dt-caption` the *utility class*; confirm before editing). Only `app/demo/page.tsx:13`'s usage is the actual `.dt-caption` utility-class D-07 targets for eyebrow-token migration; `bot-tab.tsx`'s two occurrences are the *unrelated* `--text-dt-caption` type-scale token (chat timestamp font-size, `0.8125rem`) and should be left alone unless the planner separately decides timestamps should also use the mono eyebrow register (not implied by any decision).
**Warning signs:** A find-replace of `dt-caption` → `eyebrow`-anything that touches `bot-tab.tsx`'s `text-dt-caption` classes would silently change chat-timestamp typography, which is not in scope.

### Pitfall 3: `PremiumButton`'s `icon` size stays at 40×40px even after D-13's `default` bump to 48px
**What goes wrong:** D-13 only calls out `default`/mobile-minimum sizing (48px/44px). The `icon` size variant (`size-10` = 40×40px, [VERIFIED: apps/web/shared/components/premium-button.tsx:21] `icon: 'size-10'`) is used for the header's mobile burger-menu toggle (`header.tsx:76-88`, `size="icon"`) and stays below the brief's 44px minimum mobile touch target if that constraint is read to apply site-wide rather than only to the named `default` size.
**Why it happens:** D-13's literal text scopes the 48px/44px requirement to the `coral`/`outline` variant spec ("PremiumButton's coral variant needs... min-height 48px... ≥44px minimum on mobile"), which reads as being about the CTA buttons, not the icon-only burger toggle.
