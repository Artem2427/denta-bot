# Phase 06.2 Plan 01: next-intl Locale Routing + Translated Landing Hero Summary

Stood up `apps/web`'s first-ever i18n infrastructure (next-intl 4.13.7, URL-based `uk`/`ru`/`en` locale routing with `as-needed` prefixing) and proved the phase's riskiest architectural bet end-to-end: site-wide Header/Footer chrome renders correctly translated both inside the new `[locale]` route tree (`/`, `/ru`, `/en`) and outside it, on the untouched `/blog` route, via a single root-layout `NextIntlClientProvider` that falls back to the `uk` default locale when no `[locale]` URL segment is present.

## What Was Built

- **`apps/web/i18n/{routing,request,navigation}.ts` + `apps/web/proxy.ts`** — the standard next-intl App Router five-file setup (RESEARCH.md Pattern 1), using the `requestLocale`-based `getRequestConfig` variant (not the unverified `next/root-params` variant) and Next.js 16's `proxy.ts` convention (not the deprecated `middleware.ts`). The proxy's matcher explicitly excludes `/blog` so next-intl's locale-detection/redirect logic never touches blog requests (D-09's required companion change).
- **`apps/web/app/[locale]/{layout,page}.tsx`** — new locale-scoped route tree. The layout guards against invalid locales (`hasLocale` + `notFound()`), calls `setRequestLocale` for static rendering, and is a thin pass-through with no `NextIntlClientProvider` of its own (that lives in the root layout, shared with `/blog`).
- **`apps/web/app/page.tsx` deleted** — it was a static route that would have permanently shadowed `app/[locale]/page.tsx` for the exact `/` path (Next.js gives static routes priority over dynamic segments).
- **`apps/web/modules/landing/hero.tsx`** (+ `hero-stats.tsx`, `hero-notification-badge.tsx`) — the first `modules/landing/*` component, adapted from `modules/home/hero.tsx`'s Reveal/Stat/idle-bounce/Container structure but built as a **Server Component** using `getTranslations`, with only the count-up animation and idle-bounce notification card extracted into minimal `'use client'` subcomponents. Content matches the design file's copy (`DentaBot Landing.dc.html` lines 58-76): three-line headline, subtitle, two CTAs (`#demo`/`#lead` anchors), and 3 stats (`−70%`/`24/7`/`1 день`, only the first animated).
- **`apps/web/app/layout.tsx`** — now `async`, resolves `getLocale()`/`getMessages()`, sets `<html lang={locale}>`, and wraps the existing `ThemeProvider` subtree (Header/main/Footer/Toaster) in `NextIntlClientProvider`. This is the resolution to RESEARCH.md's Open Question 1.
- **`apps/web/shared/components/header.tsx`** — nav rewired from route links (`/prices`, `/demo`, `/contacts`) to in-page anchors (`#product`, `#pricing`, `#demo`) plus Blog (kept as a real, plain `next/link`, not the locale-aware `Link`). CTAs relabeled via `useTranslations('nav')` and repointed to `#demo`/`#lead`. Locale switcher mounted in both desktop and mobile menus.
- **`apps/web/shared/components/footer.tsx`** — rewritten as a Server Component. Продукт column now anchors to `#features`/`#demo`/`#pricing`; Контакти column keeps the real email/Telegram/hours values plus a `#lead` link; the "Компанія" column (About/Privacy 404 stubs) is dropped entirely.
- **`apps/web/shared/components/locale-switcher.tsx`** — new, 3 hardcoded links to `/`, `/ru`, `/en`, active state via `useLocale()`.
- **`apps/web/messages/{uk,ru,en}.json`** — `hero`, `nav`, `footer` namespaces populated. `uk` is the canonical source (design copy verbatim); `ru`/`en` are Claude's persuasive-intent adaptations (D-10), not literal translations.
- **`apps/web/app/premium-theme.css`** — added `html { scroll-behavior: smooth }` (the existing reduced-motion override already turns it off correctly for accessibility).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Hero rewritten as a Server Component instead of a literal client-side port of `modules/home/hero.tsx`**
- **Found during:** Task 1 verification (`pnpm --filter web dev`, visiting `/`)
- **Issue:** The plan's Task 1 explicitly directs `app/[locale]/layout.tsx` to NOT wrap children in `NextIntlClientProvider` ("the root layout owns that, see Task 2's Header/Footer work"). A literal port of `modules/home/hero.tsx` (a `'use client'` component using `useTranslations`) crashes with "Failed to call `useTranslations` because the context from `NextIntlClientProvider` was not found" on every route, since no provider exists until Task 2 runs — directly contradicting Task 1's own `<verify>`/`<done>` criteria ("visit `/`, `/ru`, `/en` — confirm each renders the Hero with locale-appropriate copy").
- **Fix:** Rewrote `Hero` as an `async` Server Component using `getTranslations()` (works via server-side AsyncLocalStorage, no client provider needed), extracting only the two genuinely interactive pieces — the count-up stat animation and the idle-bounce notification card — into two small `'use client'` sibling files (`hero-stats.tsx`, `hero-notification-badge.tsx`). This matches the plan's own architecture map ("only client components needing `useTranslations` need the client provider") and RESEARCH.md's Pattern 3.
- **Files modified:** `apps/web/modules/landing/hero.tsx` (rewritten), `apps/web/modules/landing/hero-stats.tsx` (new), `apps/web/modules/landing/hero-notification-badge.tsx` (new) — the latter two are not in the plan's `files_modified` list.
- **Commit:** c5277b9

**2. [Rule 1 - Bug] Footer converted to a Server Component**
- **Found during:** Task 2, applying the same reasoning as deviation #1
- **Issue:** No functional requirement for Footer to be a client component — it has no interactive state, and making it client-side would need the same provider-dependency workaround.
- **Fix:** `Footer` is now an `async` Server Component using `getTranslations('footer')`.
- **Files modified:** `apps/web/shared/components/footer.tsx`
- **Commit:** 691a5ee

**3. [Rule 3 - Blocking issue] TS2742 "inferred type cannot be named" in `i18n/navigation.ts`**
- **Found during:** Task 1, `pnpm --filter web build`
- **Issue:** `next-intl`'s `createNavigation(routing)`'s inferred return type could not be printed by TypeScript ("The inferred type of 'Link' cannot be named without a reference to '.pnpm/@types+react@19.2.17/...'. This is likely not portable.") — caused by a pre-existing duplicate `@types/react` version across the monorepo (`apps/client-admin` pins `^19.2.17`, every other app including `apps/web` pins exact `19.2.2`).
- **Fix:** Added an explicit `ReturnType<typeof createNavigation>` type annotation to the destructured `createNavigation(routing)` call, sidestepping the need for TS to synthesize a printable inferred type.
- **Files modified:** `apps/web/i18n/navigation.ts`
- **Commit:** c5277b9

**4. [Rule 2 - Missing functionality] Added `footer.hoursLabel`/`footer.hoursValue` beyond the plan's literal namespace list**
- **Found during:** Task 2, implementing Footer translation
- **Issue:** The plan's Task 2 action text states "Wire every string through `useTranslations('footer')`" but its illustrative namespace list (`tagline, productHeading, linkFeatures, linkAdmin, linkPricing, contactHeading, linkLead, copyright`) omits keys for the "Робочі години" (business hours) label and value, which would otherwise stay hardcoded Ukrainian on `/ru`/`/en`.
- **Fix:** Added `hoursLabel`/`hoursValue` to the `footer` namespace in all 3 message files. Left "Email"/"Telegram" as static labels (deliberately not translated — they're borrowed words, identical across all 3 locales, including the `uk` canonical copy).
- **Files modified:** `apps/web/messages/{uk,ru,en}.json`, `apps/web/shared/components/footer.tsx`
- **Commit:** 691a5ee

No architectural (Rule 4) deviations — the plan's own documented architecture (chrome outside `[locale]` falling back to `uk` via the root layout) worked exactly as designed once Hero/Footer were made Server Components.
