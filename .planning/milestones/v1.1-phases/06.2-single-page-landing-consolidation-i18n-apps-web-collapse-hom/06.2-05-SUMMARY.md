## Decisions Made

- **faq.tsx as a Server Component:** The plan's Task 3 action text (unlike Tasks 1/2) doesn't specify `'use client'`. Every sibling landing module that has no interactivity of its own (`how-it-works.tsx`, `admin-showcase.tsx`, `channel-marquee.tsx`, `hero.tsx`) is an `async` Server Component using `getTranslations`. `PremiumAccordion` wraps Radix's `Accordion.Root`, which ships its own internal `'use client'` boundary inside the `radix-ui` package, so no top-level client directive is needed here either. Followed this established split rather than defaulting to `'use client'`.
- **features.tsx icon-to-item index mapping:** The plan's rationale text lists the new content's concepts in an order ("Telegram bot / shared schedule / auto-reminders / analytics / role access / reviews / reschedule-cancel / multi-branch") that doesn't literally 1:1 match `modules/home/features.tsx`'s original per-icon concept order past index 4 (e.g. new item 5 is "role access" where home's item 5 was "reviews"/Star). The plan's *literal* instruction — "SAME 8 Phosphor icons in the SAME order as `modules/home/features.tsx`" — was followed as the binding instruction: `[ChatCircleText, Calendar, Bell, ChartBar, Star, Gear, Users, Check]` mapped index-for-index onto `t.raw('items')`. This satisfies the plan's explicit `<verify>`/`<done>` (8 cards render, `check-types` passes) and its literal ordering instruction; the parenthetical concept-list is read as rationale/justification text, not an independent ordering requirement.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Adjusted verify-command interpretation for Task 1/2's literal `t.raw('features.items')` / `t.raw('reviews.items')` grep**
- **Found during:** Task 1 (features.tsx) and Task 2 (reviews.tsx)
- **Issue:** The plan's `<verify>` automated command greps for the literal substring `t.raw('features.items')` (and `t.raw('reviews.items')` for Task 2). This substring never appears in idiomatic `next-intl` code — every prior landing module in this same phase (`problem-solution.tsx`, `how-it-works.tsx`, `channel-marquee.tsx`, `hero.tsx`, `header.tsx`, `footer.tsx`) scopes the translator to its namespace first (`useTranslations('features')` / `getTranslations('features')`) and then calls `t.raw('items')` — never the unscoped dotted form. Writing `t.raw('features.items')` literally would require an unscoped root-level `useTranslations()` call, breaking from the established per-section-namespace convention this phase has used consistently (matches the 06.2-03 SUMMARY's prior note that this project's plan-authored verify greps have occasionally been imprecise, e.g. the `deleteMany`/`truncate` false-positive in seed-pricing.ts).
- **Fix:** Implemented the idiomatic, codebase-consistent pattern (`useTranslations('features')` + `t.raw('items')`) and verified equivalently: confirmed `messages/uk.json`'s `features.items`/`reviews.items` arrays have the expected length (8 and 3), confirmed `pnpm --filter web check-types` produces zero errors attributable to either new file, and confirmed `eslint` is clean on both files.
- **Files modified:** `apps/web/modules/landing/features.tsx`, `apps/web/modules/landing/reviews.tsx`
- **Verification:** `pnpm --filter web check-types` (no errors in either file — only the pre-existing, unrelated `packages/ui` csstype conflict); `pnpm exec eslint` clean; manual `node -e` check of `messages/uk.json` array lengths
- **Committed in:** `10b1a6c` (Task 1), `9e11bf3` (Task 2)
