# Phase 06.2: Code Review Report

**Reviewed:** 2026-08-19

## Summary

Reviewed the single-page landing consolidation, next-intl routing setup, the 3 retired-route redirect stubs, the PricingPlan reseed script, and the lead-capture form. The core i18n plumbing (routing.ts, request.ts, proxy.ts matcher intent, root/[locale] layout split) is sound and the reseed script correctly avoids `deleteMany`/truncate as required. However, one defect turns a downstream API hiccup into a full-site outage (no error boundary for the landing page's pricing fetch), and several i18n completeness gaps leave literal Ukrainian text baked into the hero/pricing chrome regardless of the active locale — undermining the phase's central i18n deliverable. The retired-route redirects are also locale-blind, which silently drops `/ru` and `/en` visitors back to Ukrainian.

## Critical Issues

### CR-01: Pricing-plans fetch failure crashes the entire landing page, not just the pricing section

**File:** `apps/web/app/[locale]/page.tsx:22-27`
**Issue:** `LandingPage` throws when `GET /public/pricing-plans` returns a non-OK status:
```ts
const res = await fetch(`${getServerApiUrl()}/public/pricing-plans`, {
  next: { revalidate: 60 },
});
if (!res.ok) {
  throw new Error(`Failed to fetch pricing plans: ${res.status}`);
}
```
Before this phase, this exact `!res.ok` throw only tore down the standalone `/prices` page (verified against the pre-consolidation `apps/web/app/prices/page.tsx`, commit `c5277b9^`). Now the same fetch gates the entire consolidated landing page — Hero, ChannelMarquee, ProblemSolution, HowItWorks, AdminShowcase, Features, Reviews, LeadSection, and Faq all live in the same render pass as `PricingSection`. There is no `app/[locale]/error.tsx` (or `app/error.tsx`) in this phase's file set — only `apps/web/app/blog/error.tsx` exists — so a transient backend blip on `/public/pricing-plans` takes down the *entire* marketing site (all three locales, since the layout's Header/Footer are also inside the same failing tree) with Next.js's generic unstyled error page, instead of degrading gracefully to an empty/placeholder pricing section. This is a severe increase in blast radius introduced by the consolidation.
**Fix:** Catch the fetch failure and fall back to an empty `plans` array (the code already documents that an empty array is an acceptable "reseed-failure signal" state) instead of throwing, and/or add `apps/web/app/[locale]/error.tsx` as a safety net:
```ts
let plans: PricingPlan[] = [];
try {
  const res = await fetch(`${getServerApiUrl()}/public/pricing-plans`, {
    next: { revalidate: 60 },
  });
  if (res.ok) {
    plans = (await res.json()) as PricingPlan[];
  }
} catch {
  // network/backend failure — render the rest of the landing page with an empty pricing section
}
```

## Warnings

### WR-01: Retired-route redirects always land on the default (uk) locale, discarding the visitor's ru/en context

**File:** `apps/web/app/contacts/page.tsx:8`, `apps/web/app/prices/page.tsx:7`, `apps/web/app/demo/page.tsx:8`
**Issue:** All three retired routes redirect unconditionally to `/#lead`, `/#pricing`, `/#demo` — always the unprefixed (uk) landing page. `/prices`, `/demo`, `/contacts` sit outside the `[locale]` segment (by design, per `proxy.ts`'s matcher exclusion), so there is no locale context available to preserve. Critically, this is not just a dead-bookmark concern: `apps/web/modules/demo/admin-tab.tsx:134` links directly to `routes.contacts` (`/contacts`) from *inside* the interactive demo simulation that is itself embedded on the localized landing page (`AdminShowcase` → `DemoTabs` → `AdminTab`). A visitor browsing `/en` or `/ru` who clicks "Connect your clinic" in the demo tab is silently redirected back to the Ukrainian-language landing page, losing their selected locale mid-funnel — on the primary conversion CTA.
**Fix:** Either read/forward the visitor's locale (e.g. via the `NEXT_LOCALE` cookie next-intl sets, or an explicit `?locale=` query param) before redirecting, or — simpler — change `admin-tab.tsx`'s CTA to link straight to `#lead` (same page, same tab, no locale loss) instead of routing through the retired `/contacts` stub:
```tsx
// apps/web/modules/demo/admin-tab.tsx
<Button variant="secondary" size="sm" asChild>
  <a href="#lead">Підключити свою клініку →</a>
</Button>
```

### WR-02: Hero section has hardcoded Ukrainian strings that never localize

**File:** `apps/web/modules/landing/hero.tsx:66-68`, `apps/web/modules/landing/hero-notification-badge.tsx:18`
**Issue:** The hero — the very first thing every visitor sees, on every locale — has two literal Ukrainian strings that bypass `next-intl` entirely:
```tsx
// hero.tsx
<span className="text-sm font-medium text-dt-navy">
  Нагадування відправлено 24 пацієнтам
</span>
```
```tsx
// hero-notification-badge.tsx
<span className="text-sm font-medium text-dt-navy">
  Новий запис від Олени Коваль
</span>
```
Every other string in `hero.tsx` is sourced via `t('...')` from `messages/{locale}.json`, so this is an inconsistency, not a deliberate scoping decision — `messages/*.json`'s `hero` namespace has no keys for these two badges. English/Russian visitors will see Ukrainian text mixed into an otherwise fully translated hero, directly undercutting D-08/D-09 (locale routing covering "the landing page and site chrome").
**Fix:** Add `hero.notificationBadge` / `hero.reminderBadge` keys to all three message files and consume them via `t()`/props, e.g.:
```tsx
// hero.tsx
<span className="text-sm font-medium text-dt-navy">{t('reminderBadge')}</span>
```
```tsx
// hero-notification-badge.tsx — pass the translated string in as a prop from hero.tsx
export function HeroNotificationBadge({ text }: { text: string }): React.JSX.Element {
  ...
  <span className="text-sm font-medium text-dt-navy">{text}</span>
```

### WR-03: Pricing section badge and price suffix are hardcoded Ukrainian, contradicting the component's own i18n contract

**File:** `apps/web/modules/landing/pricing-section.tsx:80`, `apps/web/modules/landing/pricing-section.tsx:91`
**Issue:** The file's own comment states: "only the surrounding chrome (heading, billing toggle, CTA, footnote) is translated via `useTranslations('pricing')`" — but two more pieces of chrome are not:
```tsx
<PremiumBadge variant="coral" className="absolute -top-4 left-1/2 -translate-x-1/2">
  Популярний
</PremiumBadge>
...
<span className="text-dt-graphite">/міс</span>
```
Neither is API-sourced data (unlike `plan.name`/`plan.description`/`plan.features`, which D-11 explicitly scopes as Ukrainian-only-by-design) — both are component-owned chrome strings that should follow the same translation path as the rest of the section.
**Fix:** Add `pricing.popularBadge` and `pricing.perMonth` keys and use them:
```tsx
<PremiumBadge variant="coral" className="...">{t('popularBadge')}</PremiumBadge>
...
<span className="text-dt-graphite">{t('perMonth')}</span>
```

### WR-04: `proxy.ts` matcher regex lacks path-segment boundaries, silently misrouting any future path that merely starts with an excluded literal

**File:** `apps/web/proxy.ts:17`
**Issue:** The matcher `'/((?!api|_next|_vercel|blog|prices|demo|contacts|.*\\..*).*)'` uses a negative lookahead with no boundary (`/` or end-of-string) after each excluded literal. Verified with the actual regex:
```
/blog        => excluded (intended)
/blogging    => excluded (unintended — not a real route today, but would be silently skipped)
/pricesss    => excluded (unintended)
/democracy   => excluded (unintended)
/contactsupport => excluded (unintended)
```
Any future route whose path merely starts with `blog`, `prices`, `demo`, or `contacts` (e.g. a hypothetical `/blog-tags`, `/demography`, `/pricesing-guide` page) would silently bypass the locale middleware — no redirect/rewrite, no locale detection — with no warning at build or runtime. This is latent, not currently triggered (no such routes exist), but it is a real correctness gap in security/routing-critical config that will bite silently later.
**Fix:** Anchor each excluded segment to a path boundary:
```ts
matcher: [
  '/((?!api/|_next/|_vercel/|blog(?:/|$)|prices(?:/|$)|demo(?:/|$)|contacts(?:/|$)|.*\\..*).*)',
],
```

### WR-05: `apps/web/i18n/navigation.ts` is entirely unused dead code

**File:** `apps/web/i18n/navigation.ts:1-9`
**Issue:** This module wraps `next-intl/navigation`'s `createNavigation(routing)` and exports `Link`, `redirect`, `usePathname`, `useRouter`, `getPathname`. Grepping the whole `apps/web` tree for actual imports (`from '@/i18n/navigation'`) turns up zero matches — `header.tsx` only *mentions* `@/i18n/navigation` in a code comment explaining why it deliberately uses plain `next/link` instead, but never imports it. Every route in this phase (`/`, `/ru`, `/en`, `/blog`) is either handled by plain `next/link`/`next/navigation`, or by hardcoded literal hrefs in `locale-switcher.tsx`. The file is scaffolding that nothing consumes.
**Fix:** Either wire it in where it was presumably intended (e.g. `locale-switcher.tsx`'s hardcoded `/`, `/ru`, `/en` hrefs could use `getPathname`/`Link` from this module for consistency with routing config changes), or delete the file if the hardcoded-link approach is intentionally permanent per the `locale-switcher.tsx` comment.

### WR-06: `seed-pricing.ts` upsert is non-atomic (check-then-act race) and matches on a non-unique field

**File:** `packages/db/prisma/seed-pricing.ts:76-87`
**Issue:** The script's own comment acknowledges `name` has no `@unique` constraint, and upserts via a manual `findFirst` → `update`/`create` sequence rather than `prisma.pricingPlan.upsert()`:
```ts
const existing = await prisma.pricingPlan.findFirst({ where: { name: plan.name } });
if (existing) {
  await prisma.pricingPlan.update({ where: { id: existing.id }, data: plan });
} else {
  await prisma.pricingPlan.create({ data: plan });
}
```
This is not atomic — two concurrent invocations of this script (or a race with a `platform-admin` write that renames/creates a plan) could both see no `existing` row and both `create`, producing duplicate rows with the same `name`. Given this is a manually-triggered seed script rather than an automated hot path, the practical risk is low, but it's worth noting the "idempotent" claim in the header comment only holds under single-invocation, non-concurrent execution.
**Fix:** Either add a genuine unique constraint on `name` (schema change, acknowledged as out of scope) and use `prisma.pricingPlan.upsert()`, or wrap the read-then-write in a transaction with appropriate isolation if concurrent execution is a realistic concern.

### IN-02: `HeroStats`'s animated stat hardcodes `70`, decoupled from the translated stat value it renders next to

**File:** `apps/web/modules/landing/hero-stats.tsx:12`
**Issue:** `AnimatedFirstStat` calls `useCountUp(70, 1800)` — a magic number independent of `messages/*.json`'s `hero.stats[0].value` (`"−70%"` in all three locales today). If a future copy edit changes the percentage in only the message files, the animated count-up will silently diverge from the displayed label.
**Fix:** Derive the target from the stat prop instead of hardcoding it, e.g. `parseInt(stats[0].value.replace(/[^0-9]/g, ''), 10)`.

### IN-03: Header's Blog nav item never shows "active" state on blog post detail pages

**File:** `apps/web/shared/components/header.tsx:66-73`
**Issue:** Active-state check is `pathname === link.href` where `link.href` is the literal `/blog`. On `/blog/[slug]` detail pages, this is always `false`, so the Blog nav item never highlights as active while reading a post — a minor UX inconsistency, not a functional break.
**Fix:** `pathname === link.href || pathname.startsWith(link.href + '/')`.
