- All shadow layers use a positive (downward) Y-offset, so every layer's upward bleed is small (≤12px) while downward bleed is large (up to 52px on hover) — this asymmetry is why the fix uses asymmetric `pt-6`/`pb-16`, not symmetric padding.

**Confirmed via `apps/web/app/layout.tsx` (root `<body>` has `overflow-x-hidden` but no `max-w`) and `apps/web/app/[locale]/page.tsx` (Reviews sits between `<PricingSection>` and `<LeadSection>`, both siblings with no wrapping max-width container):** a `<Section>` direct child with no horizontal padding of its own genuinely spans full viewport width — nothing above Reviews in the DOM tree re-imposes a max-width once we move the carousel outside `Container`.

**Confirmed via `apps/web/shared/lib/cn.ts`:** `cn()` = `twMerge(clsx(inputs))` — Tailwind class conflicts resolve last-wins per property group. Not used in this fix's approach (no conflicting `py`/`pb` combination is introduced on `Section` itself — the fix stays entirely inside `reviews.tsx`'s own JSX, not via a `className` prop into `Section`), noted here only so the executor doesn't reach for a `<Section className="pb-*">` override as an alternative — don't do that; it would `twMerge`-override Section's own fluid clamp for `padding-bottom` with a fixed value, making Section's bottom padding non-fluid, which is not desired.

**Tone check (why only the bottom edge shows visible clipping, though the same underlying risk exists on top):** Reviews and its preceding sibling `PricingSection` both default to `tone="warm-white"` (neither passes an explicit `tone` prop); `LeadSection` explicitly passes `tone="navy"`. A clip at the Reviews/PricingSection boundary (same background color) is invisible; a clip at the Reviews/LeadSection boundary (navy vs. warm-white) is stark and exactly what the user's screenshot shows.

**Root-cause mechanism for the shadow clip (confirmed via box-model first-principles, not assumed):** `Container` has no padding/margin of its own. The old `-my-14` (–56px) on the emblaRef div is its own last-in-flow descendant inside `Container`; a negative bottom margin on a last child effectively shrinks `Container`'s own computed flow-height by that amount, pulling `Container`'s bottom edge 56px above where the carousel visually renders. `Section`'s own `padding-bottom` (the fluid clamp) then starts measuring from that artificially-raised boundary. At the clamp's floor (64px), true remaining clearance before `LeadSection`'s navy box starts painting = 64 − 56 = 8px — thin enough to vanish to sub-pixel rounding, easily explaining "still clips" despite the nominal math working at wider viewports. **This mechanism is the reason the fix must not use a negative-margin-cancel trick at all**, regardless of what numeric value is chosen for it.
